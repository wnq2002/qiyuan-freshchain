## 1. 设计目标与约束

### 1.1 三条硬约束（决定了后面所有取舍）

| 约束 | 来源 | 设计后果 |
|---|---|---|
| **评委 `node src/server.js` 必须能跑起来** | 交付可复现性 | 零外部依赖，不引入框架、不引入 npm 包、不引入数据库服务 |
| **判定结论必须能对上证据，能被反驳** | C2 是本项目唯一真价值 | 判定不是一个分数，而是 `规则编号 + 责任主体 + 证据链 + 置信度` 四元组 |
| **对外结论与对内结论必须同一份** | 客户问询场景的口碑风险 | 单一 `judge()` 出口 + `toPublic()` 裁剪，不做两套逻辑 |

### 1.2 技术选型与理由

| 选择 | 理由 | 被否决的替代方案 |
|---|---|---|
| Node.js 22 内置 `node:sqlite` | 单文件数据库，零安装；SQL 本身就能证明设计严谨 | better-sqlite3（要编译）、PostgreSQL（要服务）、JSON 文件（无法做时间序列查询） |
| 原生 `node:http` | 9 个接口不值得引入框架；路由逻辑本身就是设计文档 | Express/Koa（多一层依赖，评委多一步 `npm install` 就可能失败） |
| 手写 SVG 曲线 | 时间序列图用 D3/Chart.js 是杀鸡用牛刀；手写可精确控制"超温区间高亮" | Chart.js（约 200KB，且难以标注证据区间） |
| 无构建前端（原生 ESM + hash 路由） | 打开即用，源码即产物，评审可直接读 | React/Vite（构建产物不可读，与"可查阅"要求冲突） |
| 确定性伪随机（mulberry32 固定种子） | 数据可复现是验证的前提；`Math.random()` 会让测试永远不稳定 | `Math.random()`（不可复现） |

**总依赖数：0。总代码量：约 3500 行。**

### 2.1 为什么把 `rules.js` 和 `analyze.js` 拆开

**这是本设计最重要的一个边界。**

- `analyze.js` 回答"数据长什么样"——超温在哪、持续多久、有没有断档。这是**事实层**。
- `rules.js` 回答"事实意味着谁的责任"——这是**判断层**。

分开的直接收益：加第 11 条规则只需要往 `RULES` 数组里追加一个对象，**不用改引擎、不用改测试、不用改接口**。这是让业务方（质控经理）能参与规则维护的前提。

如果两者混在一个文件里，规则维护就变成"改代码"，业务方永远进不来。

### 2.2 `rule-utils.js` 的由来

开发中 `rules.js` 需要一个"时间区间是否重叠"的工具函数，而 `analyze.js` 也需要。最初 `analyze.js` 从 `rules.js` 导入，`rules.js` 又从 `analyze.js` 导入 `regressWindow` —— 形成**循环依赖**，Node 加载顺序不同时 `regressWindow` 会变成 `undefined`，表现为运行期报错而非启动报错（极难排查）。

解法不是"调换 require 顺序"（那只是碰运气），而是把无状态纯函数下沉到第三方模块 `rule-utils.js`，两个模块都从它导入，依赖图变成无环：

```
rule-utils.js  ←  rules.js
       ↑
       └────────  analyze.js
```

## 3. 数据模型

### 3.1 五张表

```sql
waybills(          -- 运单主表
  no PK, customer, cargo,
  zone_label, zone_min, zone_max,     -- 温区定义（不同货物温区不同）
  origin, dest, plate, driver, device_id,
  status,           -- 'done' | 'transit'
  start_ts, end_ts, created_at
)

readings(          -- 温度读数（时间序列，最热表）
  id PK, waybill_no FK, ts, temp, probe
)
-- INDEX idx_readings_wb_ts(waybill_no, ts)  ← 判定时按运单+时间扫描

events(            -- 作业事件（判定的事实来源）
  id PK, waybill_no FK,
  type,             -- depart/arrive/door_open/unit_stop/depart_loaded/reject
  ts, duration_min, actor, note
)
-- INDEX idx_events_wb_ts(waybill_no, ts)

assets(            -- 设备台账（R05 判断维保是否及时要用）
  device_id PK, plate, last_maintained_at
)

judge_snapshots(   -- 判定快照（留档，可复盘）
  id PK, waybill_no FK,
  rule_id, rule_name, rule_version,   ← 版本号是复盘的关键
  party, party_name, confidence,
  detail, evidence_json, summary,
  need_manual, excursion_count, excursion_minutes, judged_at
)
```

### 3.2 三个设计决定值得单说

**① `readings` 用行存而非 JSON 字段**

-upside：可以 `WHERE ts BETWEEN ? AND ?` 只取需要的窗口，为将来上百万条读数留退路。
-downside：每票运单几十到几百行，写入有开销。
- 判断：冷链监控的真实数据量是"每车每 30 秒一个点、68 台车、一年"≈ 6000 万行，JSON 字段必然撑不住。**为真实规模设计，不为 demo 规模设计。**

**② `judge_snapshots` 必须存 `rule_version`**

冷链纠纷可能在三个月后才进入理赔谈判。如果那时规则已改到 v1.3，而库里只有结论没有版本号，就无法回答"当时是按哪条规则判的、判定是否可复现"。**存了版本号，才能重放。**

这也是为什么 `judge()` 的签名带 `ruleVersion` 参数，而不是直接读模块常量。

**③ `events` 是判定的事实来源，不是日志**

注意 `door_open` 有 `duration_min` 字段。这不是"记录了一次开门"，而是"记录了一次持续 45 分钟的开门"——因为**判定用的是持续时间，不是是否发生**。事件表若只存时间戳，规则将无法区分 2 分钟交接和 45 分钟私自开门。

### 3.3 温区随货物走

`zone_min/zone_max` 存在 `waybills` 而不是 `cargo` 字典表：同一种货物在不同客户、不同季节可能约定不同温区（比如冷冻品有的客户要 -18℃，有的接受 -15℃）。**温区是这笔交易的约定，不是货物的固有属性。**

## 4. 判定算法

### 4.1 整体流程

```
读数据库 → buildContext() → judge() → 返回判定四元组
                ↓
        ┌───────┴────────┐
        │ 1. 排序读数     │  时间序列必须有序，否则回归、空洞全错
        │ 2. 识别超温区间 │  0.5℃ 容差 + 5 分钟去抖
        │ 3. 识别采样空洞 │  相邻读数间隔
        │ 4. 计算升温窗口 │  线性回归求 ℃/h
        │ 5. 完整性判据   │  覆盖率/空洞/条数 三重
        └────────────────┘
```

### 4.2 超温区间识别：两个细节决定成败

```js
// ① 容差：仪表本身有 ±0.5℃ 误差，卡在边界上不算超温
const lo = zoneMin - 0.5, hi = zoneMax + 0.5;

// ② 去抖：单样本越界视为传感器抖动
if (g.idx.length < 2) return null;
```

**为什么去抖要求至少 2 个连续越界样本，而不是"持续 5 分钟"？**

因为 `crossTime` 会在越界样本前后做线性插值，一个单点尖峰（比如 2.0℃ → 4.8℃ → 2.1℃）插值后会被算成约 10 分钟的"超温"，刚好越过 5 分钟门槛。这个虚增是插值算法的产物，不是物理现实——真实货物有热惯性，不可能在 5 分钟内升 2.8℃ 又降回来。

所以判据改成**样本数**而非**分钟数**：物理上讲得通（热惯性导致至少两个采样点同时越界），工程上也不会被插值骗过。

> 这个改动曾导致 007 场景回归失败（空洞边缘只剩 1 个越界样本被判为抖动）。处理方式是**调整场景数据使其物理上更真实**（开门 25→45 分钟），而不是把去抖逻辑改回去。规则是对的，是场景造得不够真。

### 4.3 数据完整性：免责的举证责任高于归责

R08「温区内正常」是**免责结论**——它告诉承运方"你没责任"。这种结论一旦建立在残缺数据上，就是系统在替一方开脱。

```js
const dataComplete = coverage >= 0.6      // ① 覆盖率 ≥60%
                  && !hasBigGap           // ② 无 >20 分钟空洞
                  && rs.length >= 10;     // ③ 绝对条数 ≥10
```

**三条是"与"，不是"或"。**

开发中踩过一个坑：010 场景只有 12 条读数、中间空了 200 多分钟，但 `rs.length >= 10` 被满足了，于是系统判"温控合格"。**用 12 个点给一整趟运输背书。** 改成三重判据后，同一场景正确落到 R10「证据不足，须人工介入」。

原则写成一句话：**归责可以基于"排除法"，免责必须基于"完整证据"。**

### 4.4 R02 vs R07：规则分不开，说明模型没建对

这是全项目最有价值的一次排查。

**现象**：003 场景（预冷不足，货物带热上路）和 008 场景（制冷能力不足，4 次合规开门后压不回去）在数据上几乎一样——都是"出发后温度缓慢上升"。规则无法区分，两种场景被判成同一条规则。

**第一反应**（错的）：调阈值。加大斜率门槛、缩窄观察窗口。结果是把 003 判对了，008 又判错了。**本质是两个物理过程在数据上不可分，调阈值只是把分界线左右搬。**

**正确做法**：回去改物理模型。

```js
// 旧模型：固定升温速率（无法表达"货物带热会自己散掉"）
temp += riseRate * step;

// 新模型：指数衰减热源（货物带热是有限热量，会耗尽）
if (cargoHeat && m >= cargoHeat.at) {
  const dtau = m - cargoHeat.at;
  temp += cargoHeat.q0 * Math.exp(-dtau / cargoHeat.tau) * step;
}
```

改完之后，两个场景在**物理行为**上天然分开：

| | 预冷不足（003） | 制冷不足（008） |
|---|---|---|
| 升温形态 | 先陡后缓，指数衰减 | 每次开门后升温，且**回不到基线** |
| 30 分钟最陡斜率 | > 2.0 ℃/h | 每次 1.5~2.5 ℃/h，但方向反复 |
| 末段是否回落 | 是（货物热量散尽） | 否（制冷能力就是不够） |

于是 R02 的判据从"升温快"升级为"**升温快 + 末段能回落到基线 +1.0℃ 内**"，R07 接住"回不去"的那一类。

**教训写进 `gates/gate-02`**：规则分不开的两件事，不要改阈值，要改领域模型。

### 4.5 最陡子窗搜索：固定窗口的失败

003 场景的升温峰值出现在出发后 **20–50 分钟**。如果固定取「出发后 30–60 分钟」这个窗口做回归，会把后面的回落段摊进来，斜率被稀释到 1.8 ℃/h，低于 2.0 门槛，漏判。

```js
// 60 分钟观察域内，每 5 分钟滑动一次，找最陡的 30 分钟子窗
for (let off = 0; off <= 30; off += 5) {
  const from = depart.at + off * 60000;
  const w = regressWindow(readings, from, from + 30 * 60000);
  if (!steepest || w.slope > steepest.slope) steepest = w;
}
if (!steepest || steepest.slope <= 2.0) return null;
```

**基线的取法同样重要**：最初取「出发后 0–90 分钟均值」做基线，而这段里包含了 6.7℃ 的峰值 —— 基线被自己污染，导致"末段回落判据"永远不成立。改为**取出发瞬间 ±5 分钟**，基线才代表真实起运温度。

### 4.6 规则短路求值

```js
const ordered = [...RULES].sort((a, b) => a.priority - b.priority);
for (const r of ordered) {
  const hit = r.test(ctx);
  if (hit) return { ruleId: r.id, ...hit };
}
```

优先级顺序（数字小者优先）：

```
R01 装车温度不合格 (10)  → 出库就超标的，责任在源头，先判
R06 数据缺失       (20)  → 数据不可信时，后面所有判定都不成立
R05 机组停机       (30)  → 硬件故障是硬证据
R03 途中开门超时   (40)  → 人工作业违规
R04 卸货超时       (50)  → 收货端作业违规
R02 预冷不足       (60)  → 货物初始状态问题
R07 累积超温       (70)  → 多次小超温累计（最"软"的归责）
R09 温控合格被拒收 (80)  → 反证：温控没问题，问题在收货方
R08 温区内正常     (90)  → 免责结论放最后
R10 证据不足       (999) → 兜底
```

**为什么 R01 排第一**：如果装车时就已经 7.5℃，那么途中的一切温升都是果不是因，判承运方是错的。**先判因果链上游。**

**为什么 R06 排第二**：数据不可信时，任何"温控合格"的结论都不成立。它不是"某方责任"，而是"这次判定本身无效"。

**为什么 R10 兜底在 999 而不是"默认归承运方"**：这是本设计刻意避免的行业惯性。默认归责承运方是最常见的产品设计错误——它让系统在证据不足时**假装有结论**，而错误归责的代价由承运方承担。R10 明确输出「无法判定 + 需人工介入」，把不确定性暴露给人，而不是藏进一个假结论里。

### 4.7 在途运单不判责

```js
if (ctx.waybill.status === 'transit') {
  return { ruleId: 'IN_TRANSIT', ruleName: '在途监测',
           party: 'PENDING', partyName: '在途未定责',
           confidence: null, ... };
}
```

货还在路上就出最终结论，等于**提前定罪**。而且技术上必然出错——途中的超温可能被后续的制冷恢复，最终到货时完全合格。

所以 `PENDING` 状态携带 `confidence: null`（不是 0，是"还没有"），看板单独用青色标记，不计入 `stats.byParty` 的责任统计。

同时 `alertLevel()` 对 PENDING 单独分级：**有超温才告警**（≥30 分钟为 critical），没超温就是正常。这样在途运单既不会漏掉真实风险，也不会因为"还没走完"就常年显示异常。

## 5. 接口契约

### 5.1 九个接口

| 方法 | 路径 | 用途 | 视图 |
|---|---|---|---|
| GET | `/api/health` | 健康检查，返回规则版本与条数 | — |
| GET | `/api/dashboard` | 质控看板：全部运单 + 统计 + 告警排序 | 内部 |
| GET | `/api/waybills?status=` | 运单列表（可按状态过滤） | 内部 |
| GET | `/api/waybills/:no` | 运单详情（读数/事件/超温/判定） | 内部 |
| GET | `/api/waybills/:no/judgement` | 仅判定结论 | 内部 |
| GET | `/api/waybills/:no/stream` | SSE 实时推送 | 内部 |
| GET | `/api/track/:no` | 客户问询 | **对外（脱敏）** |
| GET | `/api/rules` | 规则清单与责任主体字典 | — |
| POST | `/api/ingest` | 设备上报读数，即时复判 | — |

### 5.2 同源同值：这是对外承诺的技术保障

```js
// 内部
const d = analyzeWaybill(no);
return send(res, 200, d.verdict);

// 对外
const d = analyzeWaybill(no);
return send(res, 200, toPublic(d));
```

**两次调用同一个 `analyzeWaybill()`，对外只经 `toPublic()` 裁剪字段，不改任何判定值。**

集成测试里有专门的断言逐项比对：

```js
test('客户问询与内部判定：结论必须同源同值', ...);
// ruleId / partyName / confidence / detail 逐项相等
```

这个设计防的是一种很常见的翻车：内部说承运方责任，客服系统说是收货方责任，客户把两张截图发到群里。

### 5.3 脱敏边界

`toPublic()` 剥掉的字段：

| 剥掉 | 原因 |
|---|---|
| `driver`（司机姓名） | 个人信息，不该出现在客户可见页面 |
| `device_id`（设备编号） | 设备编号可反查到车辆，属于承运方内部资产信息 |
| `plate`（完整车牌） | 同上 |

保留 `customer / cargo / zone / origin / dest / 温度曲线 / 事件类型与时点` —— 这些是客户本来就知道的，也是他质疑判定时需要的依据。

**注意保留 `evidence` 证据链**：脱敏不等于"少说"，客户必须能看到"为什么判我"。少给证据会让问询变成吵架。

集成测试断言：`body` 中不含 `'陆文斌'`（司机名）、不含 `'RC-2023-0460'`（设备号）。

### 5.4 设备接入契约

`POST /api/ingest` 是将来对接真实记录仪的入口：

```json
{
  "waybillNo": "LT20261118012",
  "readings": [
    { "ts": 1763500000000, "temp": 7.2, "probe": "REAR-1" }
  ]
}
```

响应：

```json
{ "accepted": 1, "verdict": {...}, "excursions": 2 }
```

**要点**：
- `ts` 是**毫秒时间戳**（与库内一致），不是字符串。厂商协议适配器的职责就是把各种格式转成这个。
- 写入后**立即复判并返回新结论**，调用方不用再查一次。
- 校验：非有限数值直接 400，不静默丢弃（静默丢弃会导致"数据缺失"被误判成设备问题）。
- `body > 1MB` 直接断开，防止单次上报撑爆内存。

**当前局限**：演示环境没有真实设备，`/stream` 的"实时"由模拟器按 `Math.sin(tick/3)*0.15` 造出微小波动。生产环境应改为订阅设备上报流，并在 `handleStream` 里把 `projected` 换成真实最新读数。这一点在 `docs/06` 的"未解决问题"中再次声明。

## 6. 前端设计

### 6.1 四个页面与三条角色路径

| 页面 | 路由 | 角色 | 这页要回答的问题 |
|---|---|---|---|
| 质控看板 | `#/` | 质控主管 | "现在哪几票出事了？先看哪票？" |
| 运单详情 | `#/waybill/:no` | 质控/理赔 | "这票为什么判他？证据在哪？" |
| 客户问询 | `#/track` | 客服/客户 | "我的货怎么样？谁的责？" |
| 规则说明 | `#/rules` | 所有人 | "你凭什么这么判？" |

第四条容易被忽略，但对**信任**至关重要。冷链定责本质是争议解决，如果判定依据不透明，客户第一反应是"你系统乱判"。把 R01–R10 连同优先级、执行顺序、业务含义全部摆出来，是让规则可被质询的前提。

### 6.2 手写 SVG 温度曲线

`tempChart(detail)` 生成的图形包含四层：

1. **温区带**：`zone_min`~`zone_max` 的浅色背景带宽，让人一眼看出"应该在哪"
2. **超温高亮**：`excursions` 区间用红/琥珀色矩形叠加，标注峰值
3. **曲线**：`readings` 折线，`M...L...` 逐点拼接
4. **双向刻度**：左侧温度、底部时间

**为什么不用图表库**：需要把"超温区间"和"曲线"在同一坐标系上精确对齐并高亮。图表库要么不支持区间标注，要么需要额外插件；手写 200 行 SVG 反而更短、更可控、生成的 DOM 还能被 E2E 测试直接断言（`paths[0].split('L').length > 50`）。

### 6.3 设计红线（自检项）

- 禁止紫粉渐变、禁止 emoji、禁止"赋能/闭环/抓手"式文案
- 主色冷链青蓝 `#0d7d8f`，告警红 `#c4361f`，琥珀 `#b5730c`，合格绿 `#0d7d5f`
- 所有数字带单位；所有时间显示为东八区 `MM-DD HH:mm`

理由：这是一套要给**质控员每天看 8 小时**的界面，不是给投资人看的 demo。克制比漂亮重要。

## 7. 关键取舍记录

| 取舍 | 选择 | 放弃了什么 | 为什么 |
|---|---|---|---|
| 判定输出形态 | 四元组（规则+主体+证据+置信度） | 单一"责任分" | 分数无法被反驳，无法用于理赔谈判 |
| 证据不足时 | 输出 R10「无法判定」 | 默认归承运方 | 错误归责的代价由一方承担，比"没有结论"更糟 |
| 在途运单 | PENDING，不判责 | 提前给出实时结论 | 提前定罪 + 技术上必然出错 |
| 数据缺失 | 单独成规则（R06） | 当作"无异常"跳过 | 数据缺失本身可能就是设备方的责任 |
| 规则存储 | 数据结构（数组） | 硬编码 if-else | 业务方要能加规则 |
| 数据库 | 单文件 SQLite | 云数据库 | 可复现 > 可扩展（本期） |
| 前端 | 无构建 | React | 源码可读 > 开发效率（本期） |

| 在途是否不判责 | ✅ | 单测 + 011/012 场景 |
| 数据缺失是否阻断裂免 | ✅ | 010 场景判 R10 |

**遗留风险（不在本期解决，如实列出）**：

1. 阈值（2.0 ℃/h、45 分钟、60 分钟）来自行业通行惯例，**未与冷鲜通真实业务校准**。
2. 单探头假设。真实冷藏车有 2–3 个探头，多点冲突时的裁决逻辑未做。
3. R02 与 R07 的样本各只有 1 个场景，边界覆盖不足。
4. SSE 的"实时"是模拟，非真实设备流。
5. 无鉴权。任何人拿到 URL 都能看内部视图。生产环境必须加登录与角色隔离。
