# 02 · 客户背景（教学虚构）

> ⚠️ 本文件依据考核任务书中的一句话需求反推补全。任务书原文指向《冷鲜通_客户背景》，该文件未随考核包提供，故按行业常识虚构，**全部主体、数据均为教学虚构，不含任何真实客户信息**。反推依据与推断标注见文末。

---

## 一、企业概况

| 项 | 内容 |
|---|---|
| 名称 | 冷鲜通冷链物流有限公司 |
| 性质 | 区域性第三方冷链物流（3PL） |
| 成立 | 2013 年 |
| 规模 | 员工 210 人；自有冷藏车 68 台，外协车 40 余台 |
| 年营收 | 约 1.4 亿元 |
| 覆盖 | 以省会为中心，辐射省内 11 个地市及周边两省，单程最长 780 公里 |
| 温区 | 冷冻（-18℃ 以下）、冷藏（0~4℃）、恒温（10~15℃）三类 |
| 客户结构 | 生鲜连锁超市 38%、食品加工厂 27%、医药流通 18%、餐饮供应链 17% |

## 二、业务形态

- **主力业务**：为连锁商超与食品厂做**干线 + 城配**冷链运输，日均发运 260 余票。
- **典型运单**：从食品厂冷库提货 → 干线运输 → 区域分拨中心 → 城配至门店，涉及 2~3 次装卸。
- **温控方式**：机械制冷机组 + 车载温度记录仪（每 5 分钟一条，1~3 个探头），司机可手动开关厢门。
- **结算方式**：按吨公里计价，合同含温度考核条款（超温扣款 / 赔付）。

## 三、痛点（按客户原话推断）

### 3.1 "实时看住冷链" —— 其实是看不住

- 温度记录仪数据存在**设备厂商平台**，导出要走申请流程，最快次日拿到。
- 车辆在途时，调度只能靠司机电话报备；司机不报，就没人知道。
- 2023 年发生过一起典型事故：一车冷冻水饺因机组故障，厢温从 -20℃ 升到 -6℃ 持续 4 小时，**到货才发现**，整车报废，直接损失 18 万元。

### 3.2 "说清是谁的责任" —— 其实是说不清

这是最痛的一条。一起超温事故，往往牵涉五方：

| 主体 | 常见抗辩 |
|---|---|
| 发货方（食品厂） | "我出库时是合格的，检验单在这" |
| 承运方（冷鲜通） | "我车没问题，是他装车装太久" |
| 司机 | "我按时送到了，是收货方卸货拖了 3 小时" |
| 收货方（门店/分拨） | "到货就是坏的，你自己看" |
| 设备方 | "记录仪数据不连续，不能作为依据" |

现实处置：调度翻微信聊天记录、翻纸质交接单、打电话核对 → 三方各让一步 → **赔付了事**。2023 年因温度问题产生的赔付与扣款合计约 96 万元，其中**超过一半无法确认责任归属**，属于"和稀泥"式支出。

更严重的是**没有留痕**：同一类事故第二次发生，仍然从头吵一遍，因为没有可复用的判定依据。

### 3.3 "客户问起来能马上回答" —— 其实答不上来

- 商超客户（尤其生鲜连锁）会在到货后追问："这车货路上温度怎么样？"
- 目前客服的做法：找调度 → 找设备厂商导出数据 → 人工整理 → 微信发图。**平均响应 1.5 天**，且不同客服答的口径不一致。
- 有 2 家商超客户已在合同中加入"温度数据 24 小时内可查"条款，**当前无法满足**，存在续约风险。

## 四、决策链与项目约束（推断）

| 项 | 内容 |
|---|---|
| 项目发起人 | 总经理（亲历过 18 万报废事故） |
| 业务负责人 | 质控部经理（3 人团队，负责温控考核与赔付认定） |
| 关键干系人 | 客服主管（对客户问询负责）、调度主管（对在途负责） |
| 硬约束 | 10 周上线；预算 120 万；**不能停运改造**；司机端不能增加操作负担（否则抵触） |
| 隐性约束 | 医药客户涉及 GSP 合规，但本期不做医药专属合规功能 |

## 五、为什么是"一句话"需求

客户是区域 3PL，不是软件公司，**无法自己写出 PRD**。总经理的原话就是他的全部需求表达——这也是启元这类定制开发公司最典型的开局：客户给的是**他想要的画面**，不是需求清单。

这正是《启元软件 AI Native 转型设计》中"需求在层层翻译中失真"的现场：如果把这句话直接交给产品经理写 PRD，大概率会写成"温度监控大屏 + 告警列表 + 报表导出"——**把最值钱的"定责"整段丢掉**。本项目的做法是先做需求深访与结构化拆解（见 `01-诊断与范围冻结.md`），再用 MoSCoW 冻结基线（见 `03-需求基线MoSCoW.md`）。
