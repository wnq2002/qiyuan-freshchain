## 1. 验证策略：四层 + 一把尺子

常见的交付验证是这样的：跑通了接口，截个图，写"功能正常"。这种做法无法回答两个致命问题——**判得对不对**、**换个数据还对不对**。

本项目采用四层验证，每层回答一个不同的问题：

| 层次 | 回答的问题 | 手段 | 用例数 |
|---|---|---|---|
| L1 规则真值 | 判定**结论**对不对 | 12 个场景预置真值，引擎独立判定，两边互不知情 | 10/10 已交付场景 |
| L2 单元 | 判定**零件**对不对 | 对超温识别/空洞/回归/完整性逐函数断言 | 20 |
| L3 集成 | 判定**链路**对不对 | 真实 HTTP 请求真实服务，断言响应内容 | 17 |
| L4 端到端 | 用户**能不能用** | 无头 Chrome 渲染真实 DOM 后断言，不是测接口 | 6 |

**总计：44 项自动化测试 + 10 项真值校验，全部通过。**

### 1.1 为什么必须有 L1「真值校验」

这是本项目验证体系的地基。

如果只测"接口返回 200"、"返回里有 ruleId 字段"，那么一个把所有运单都判成 R08「无责任方」的系统也能全部通过 —— 它返回了符合结构的数据。

真值校验的做法：

```js
// scenarios.js 里预先声明（写在造数据的时候，不是看到结果之后）
expect: { ruleId: 'R02', party: 'SHIP', note: '装车 4.2℃ 合格，出发后升温超 2℃/h' }

// verify-rules.js 里独立判定（只把数据喂给引擎，不告诉它期望）
const got = judge(ctx);

// 两者比对
if (got.ruleId !== sc.expect.ruleId) → 失败
```

**关键在"互不知情"**：期望值写死在场景定义里，判定引擎只接收数据、不知道期望。这样才叫校验，否则是自证。

第一次跑这套校验，**10 个场景只对了 4 个**。这个 4/10 是本次交付最有价值的产出之一，详见 §3。

**这一步发现了一个真实问题**：首版 `renderDom` 用 `execFileSync` 调 `chrome --dump-dom`，结果测试永久挂起 —— Chrome 打印完 DOM 后进程不退出（headless 下驻留），`execFileSync` 就一直等。10 分钟无输出。

## 3. 缺陷记录（本次交付最值钱的部分）

首轮真值校验 4/10。以下是查出的缺陷，按严重程度排序。

### 3.1 R03 把「卸货开门」误判为「途中私自开门」——责任判反（最严重）

**现象**：005 场景（收货方卸货超时）被判成承运方途中开门。

**根因**：R03 的条件只是 `door_open && durationMin > 10`，没有限定时间域。卸货时开门 140 分钟，自然满足「开门超 10 分钟」，于是被判成承运方违规。

**影响**：这是**把责任判给了错误的一方**。系统对外输出「承运方责任」，承运方拿证据一看是卸货时开的门，系统立刻失信。

**修复**：

```js
const arrive = ctx.events.find(e => e.type === 'arrive');
const depart = ctx.events.find(e => e.type === 'depart');
const inTransit = (e) => (!depart || e.at >= depart.at) && (!arrive || e.at < arrive.at);
const doors = ctx.events.filter(e => e.type === 'door_open' && e.durationMin > 10 && inTransit(e));
```

**教训**：**规则必须绑定作业阶段。** "开门"这个动作在装车、途中、卸货三个阶段含义完全不同，物理事件相同但责任归属相反。脱离阶段谈行为，必然判反。

### 3.2 R08 用不完整数据为一方免责——安全漏洞

**现象**：010 场景只有 12 条读数、中间空 200 多分钟，系统判「无责任方 · 温控合格」。

**为什么这是漏洞，不是 bug**：R08 是免责结论。用 12 个点给一整趟运输背书，等于系统在替承运方开脱。 colder 一点的场景：设备方故意断电掩盖超温，系统反而说"温控合格"。

**修复过程走了两步（第一步是错的）**：

```js
// 第一次修复：加条数下限
if (!ctx.readings || ctx.readings.length < 10) return null;
```

结果 010 场景还是判 R08 —— 因为它刚好有 12 条读数，**越过了这条线**。这是"拍脑袋定阈值"的典型失败：定一个数字，然后用一个刚好卡线的场景把它绕过。

```js
// 第二次修复：三重判据，缺一不可
const dataComplete = coverage >= 0.6      // 覆盖率
                  && !hasBigGap           // 无 >20 分钟空洞
                  && rs.length >= 10;     // 绝对条数
if (!ctx.dataComplete) return null;
```

**教训写成原则**：**免责结论的举证责任必须高于归责结论。** 归责可以基于"排除法"（其他原因都排除了），免责必须基于"完整证据"。

### 3.3 R02 / R07 无法区分「货物带热」与「制冷不足」—— 物理模型太粗

**现象**：003（预冷不足，货物自带热量）和 008（制冷能力不足，多次开门后压不回去）数据形态几乎一样，都是"出发后缓慢升温"，规则无法区分。

**第一次尝试（错的）**：调阈值。加大斜率门槛到 3.0，003 判对了；但 008 的单次斜率只有 1.5~2.5，全都漏判。

**想清楚之后**：两个场景的物理过程本来就不同——货物带热是**有限热量，会散尽**；制冷不足是**持续能力缺陷，散不尽**。旧模拟器用固定升温速率，物理上无法表达"热量会耗尽"这件事，所以数据上不可分。

**这不是代码 bug，是领域模型没建对。**

**修复**：改模拟器，引入指数衰减热源。

```js
// 旧：固定升温速率（无法表达热量耗尽）
temp += riseRate * step;

// 新：指数衰减热源
if (cargoHeat && m >= cargoHeat.at) {
  const dtau = m - cargoHeat.at;
  temp += cargoHeat.q0 * Math.exp(-dtau / cargoHeat.tau) * step;
}
```

配合 R02 增加判据「**末段须回落到基线 +1.0℃ 内**」：

```js
if (lateAvg > baseAvg + 1.0) return null;  // 没回落 → 制冷不足，交给 R07
```

改完后两类场景在物理行为上天然分开，规则不用调阈值也能分开。

**教训（已写入 Gate 2 文档）**：**规则分不开的两件事，说明领域模型没建对。改模型，不要改阈值。**

### 3.4 固定 30 分钟窗口漏判（003 场景）

003 的升温峰值在出发后 **20–50 分钟**。固定取「出发后 30–60 分钟」窗口做回归，会把后面的回落段摊进来，斜率被稀释到 1.8 ℃/h，低于 2.0 门槛 → 漏判。

**修复**：60 分钟观察域内，每 5 分钟滑动一次，找最陡的 30 分钟子窗。

```js
for (let off = 0; off <= 30; off += 5) {
  const from = depart.at + off * 60000;
  const w = regressWindow(ctx.readings, from, from + 30 * 60000);
  if (!steepest || w.slope > steepest.slope) steepest = w;
}
```

### 3.5 基线被峰值污染

R02 的"是否回落"判据需要一个基线。最初取「出发后 0–90 分钟均值」，而这段里正好包含了 6.7℃ 的升温峰值 —— **基线被自己污染**，虚高到 5.4℃，导致"末段回落"永远不成立。

**修复**：基线取出发瞬间 ±5 分钟。

```js
const basePts = ctx.readings.filter(r => r.ts >= depart.at - 5*60000 && r.ts <= depart.at + 5*60000);
```

**教训**：算基线时，样本区间不能包含待检测的现象本身。

### 3.6 模拟器开门升温系数失真

最初用 0.35 ℃/min（来自冰箱开门经验），结果 8 分钟开门升温 2.8℃，导致 001 场景（合规操作）误报超温。

**修复**：改为 0.15 ℃/min。依据：冷藏车车厢体积大、冷量储备足，实测开门升温约 0.1~0.2 ℃/min。**参数要有实测依据，不能从别的场景类比。**

### 3.7 在途运单被判「无责任方」—— 业务语义缺失

**现象**：011 在途运单被判 R08「无责任方 · 温控合格」。

**为什么这是问题**：货还在路上，系统就说"温控合格、没人有责任"。如果两小时后超温了，这份结论就是错的；而且它给客户传递了"这票没事"的错觉。

**修复**：`judge()` 前置返回 `PENDING / IN_TRANSIT`。

```js
if (ctx.waybill.status === 'transit') {
  return { ruleId:'IN_TRANSIT', ruleName:'在途监测', party:'PENDING',
           partyName:'在途未定责', confidence: null, ... };
}
```

注意 `confidence: null` —— 不是 0（0 表示"有结论但很不可信"），是"还没有结论"。同时在 `alertLevel` 里单独分级：**有超温才告警**，没超温显示正常；`stats.byParty` 排除 PENDING，不让在途票污染责任统计。

**教训**：**未完成的状态不要输出最终结论。** 这不是技术问题，是业务伦理问题。

### 3.9 页面同时显示两个互相矛盾的温度要求（最终自检发现）

**现象**：交付前逐页截图检查，003 票详情页上同时出现：

- 货物名：`疫苗类生物制品（2~8℃）`
- 温区要求：`冷藏 0~4℃`

**一页上两个不同的温度要求。** 系统判定逻辑没错（用的是 `zone_min/zone_max` 字段，货物名只是个展示字符串），但对客户来说这就是"你们的系统自己都没说清要几度"。

**根因**：`scenarios.js` 里货物名是手写的展示文本，温区是 `zone: 'chilled'` 引用常量。两者从不同源，改一个不会提醒改另一个。

**为什么 44 项测试全绿却抓不到**：所有测试都在验"判定结果对不对"，没有任何测试在验"展示数据自身是否自洽"。这类问题只有**人眼看页面**才能发现。

**修复**：① 改货物名为 `冷藏注射剂（0~4℃）`、`冷藏生物制剂（0~4℃）`；② **加一条自动化测试锁住这个约束**——从货物名里正则提取温度区间，与该运单实际温区定义逐项比对。

**教训**：**功能测试保证"系统按设计工作"，一致性检查保证"设计本身没说错话"。** 两者是不同的东西，后者经常被完全忽略。这条测试加进去之后，同类矛盾（改温区忘了改货物名）不会再溜过去。

## 4. 性能

实测（Node 22，MacBook，数据为 12 票运单 / 每票约 65 条读数）：

```
buildDashboard(12 票全量判定) × 300 次
  → 单次 0.92 ms，约 1083 次/秒

analyzeWaybill(单票) × 300 次
  → 单次 0.072 ms

getReadings(单票) × 1000 次
  → 单次 0.020 ms
```

**索引确认生效**：

```
EXPLAIN QUERY PLAN
SELECT * FROM readings WHERE waybill_no=? ORDER BY ts
→ SEARCH readings USING INDEX idx_readings_wb_ts (waybill_no=?)
```

不是全表扫描。

**规模推算**：真实场景 68 台车、每车每 30 秒一个点、单车单趟 8 小时 ≈ 960 点。单票判定耗时随读数线性增长，按当前 0.072ms / 65 点推算，单票约 1.1ms。看板若需汇总 68 台车当前在途，约 75ms —— 远低于 1 秒的可接受阈值。

**但要说清楚**：这是**未做规模压力测试前**的估算，不是实测。真实数据的行数、并发、SQLite 写入锁竞争都未验证。

## 5. 现在能证明什么，不能证明什么

### 5.1 能证明

| 结论 | 证据 |
|---|---|
| 10 条规则在 10 个场景上判定正确 | L1 真值校验 10/10，脚本可复现 |

### 5.2 不能证明（如实列出）

**这七条比上面八条更重要。** 一个只讲自己多行的验证报告，可信度低于一个敢说边界的报告。

1. **判定规则对不对，只在我的虚构场景上验证过。**
   场景是我造的，真值是我定的。10/10 只说明"引擎按我的设计工作"，不说明"我的设计符合冷鲜通的真实业务"。**必须拿客户真实历史运单（含已结案理赔的）做回测，才知道规则准不准。**

2. **阈值没有校准。** 2.0 ℃/h、45 分钟、60 分钟卸货、10 分钟开门 —— 全部来自行业通行惯例，没有一条与冷鲜通的实际操作规范核对过。

3. **单探头假设。** 真实冷藏车 2–3 个探头，多点冲突时如何裁决（取最大值？取平均？按位置加权？）完全没做。这是真实的工程缺口。

4. **R02 与 R07 各只有 1 个场景。** 边界覆盖不足。特别是"货物带热 + 制冷也弱"的叠加情况，完全没有场景。

5. **性能是估算不是实测。** 未做 68 车 × 一年量级的压力测试，未测并发写入（SQLite 单写锁在真实设备高频上报下可能是瓶颈）。

6. **SSE 的"实时"是模拟的。** `handleStream` 里的 `projected` 由 `Math.sin(tick/3)*0.15` 生成，不是真实设备读数。接真设备需替换此处。

7. **无鉴权。** 任何人拿到 URL 都能访问内部视图（含司机姓名、设备编号）。生产环境必须加登录与角色隔离。
