# 06 交付说明

> 这份文档回答四个问题：**怎么跑、怎么用、能干什么、不能干什么。**
> 前三个是承诺，第四个是诚实。

## 一、5 分钟跑起来

### 1.1 环境要求

| 项 | 要求 |
|---|---|
| Node.js | **≥ 22**（必须，需内置 `node:sqlite`） |
| 数据库 | 无需安装（SQLite 单文件，随项目走） |
| 依赖包 | **无**（不需要 `npm install`） |
| 网络 | **不需要**（全部本地） |
| 浏览器 | Chrome / Edge / Safari 任一现代浏览器 |

检查 Node 版本：

```bash
node -v      # 应为 v22.x 或更高
```

### 1.2 三步启动

```bash
cd qiyuan-freshchain

# ① 初始化数据库与虚构数据（约 3 秒）
node scripts/seed.js

# ② 启动服务
node src/server.js

# ③ 浏览器打开
#    http://localhost:8787
```

启动成功会看到：

```
冷鲜通冷链监控系统已启动: http://localhost:8787
规则版本 v1.0 · 内置规则 10 条
如无数据，请先执行: node scripts/seed.js
```

### 1.3 验证跑对了

另开一个终端：

```bash
curl -s localhost:8787/api/health
```

期望输出：

```json
{"ok":true,"ruleVersion":"v1.0","rules":10,"ts":...}
```

如果 `ok` 为 `true`，服务正常。

### 1.4 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `Cannot find module 'node:sqlite'` | Node 版本 < 22 | 升级 Node |
| `SQLITE_CANTOPEN` | `data/` 目录不存在 | 先跑 `node scripts/seed.js` |
| 端口被占用 | 8787 已有服务 | `PORT=8899 node src/server.js` |
| 页面空白 | 未 seed，无数据 | 跑 `node scripts/seed.js` |
| 数据看起来是旧的 | 库文件残留 | 删 `data/freshchain.db*` 后重新 seed |

## 二、三条演示路径

固定路径，每条都走到结论。**建议按顺序演示，因为第 3 条是回答"你凭什么这么判"。**

### 路径 A：质控主管 —— "现在哪几票出事了？"

1. 打开 `http://localhost:8787`（默认进看板）
2. 看到 12 票运单，**4 票严重告警置顶**
3. 观察排序逻辑：严重 → 警告 → 轻微 → 无法判定 → 正常；同级别按超温时长降序
4. 点第一行 `LT20261118006`（机组停机 145 分钟）

**这一页要传达的**：质控员每天上班第一眼，就知道今天要处理哪几票。

### 路径 B：客服 / 客户 —— "我的货怎么样？谁的责？"

1. 点导航「客户问询」→ `http://localhost:8787/#/track`
2. 输入运单号 `LT20261118003`，查询
3. 得到结论：**发货方责任 · 预冷不足（R02）· 置信度 80%**
4. 看到证据链：
   - 出发温度 3.6℃（温区内，合格）
   - 最陡 30 分钟斜率 4.93 ℃/h（阈值 >2.0）
   - 期间无开门、无停机
   - **升温后已自行回落**（出发基线 3.5℃ → 末段均温 2.9℃）

**这一步是全场最重要的演示**：把"货物带热上路"和"制冷能力不足"分开。两者数据形态相似，靠"是否回落"区分。

5. **关键验证**：打开 `http://localhost:8787/#/waybill/LT20261118003`（内部详情页），对比结论 —— **规则编号、责任主体、置信度、判定说明，逐字相同**。

**这一页要传达的**：客户看到的就是内部看到的，没有两套口径。

### 路径 C：质疑者 —— "你凭什么这么判？"

1. 点导航「规则说明」→ `http://localhost:8787/#/rules`
2. 看到 R01–R10 十条规则，每条含：编号、名称、责任主体、优先级、业务含义
3. 看到执行顺序说明（短路求值，数字小者优先）
4. 找到 R10「证据不足」在最后（优先级 999）

**这一页要传达的**：

> 我们不默认归责任何一方。证据不足时说「无法判定，需人工介入」，而不是猜一个责任人。

这条对建立信任的作用大于前两页之和。

### 路径 D（可选）：在途运单 —— "货还在路上"

1. 看板找 `LT20261118012`（青色「在途未定责」标记）
2. 状态为「在途」，**但告警等级是 critical**
3. 判定结论显示：`IN_TRANSIT`，责任主体「在途未定责」，置信度 `null`
4. 详情里写：「在途已出现 1 段超温，累计 68 分钟，请立即联系司机核实」

**这一页要传达的**：**在途不判责，但要告警。** 货还在路上就出最终结论等于提前定罪；但超温了不报警就是失职。两个都要做到。

## 四、这套系统现在能干什么

| 能力 | 具体行为 | 在哪 |
|---|---|---|
| **C1 实时监控** | 12 票运单温度曲线、超温区间高亮、告警分级排序、SSE 实时刷新 | 看板 `/` |
| **C2 责任判定** | 每票输出「规则编号 + 责任主体 + 证据链 + 置信度」，10 条规则短路求值 | 详情页 `/waybill/:no` |
| **C3 客户问询** | 按运单号查结论，与内部同源同值，自动脱敏 | 问询页 `/track` |
| **规则可查阅** | R01–R10 全部规则、优先级、业务含义、执行顺序 | 规则页 `/rules` |
| **设备数据接入** | `POST /api/ingest` 接收读数并即时复判 | 接口 |
| **判定留档** | 判定快照入库，含 `rule_version`，可事后复盘 | 数据库 |
| **在途监测** | 在途不判责但告警，超温即提示核实 | 看板 + 详情 |

## 五、这套系统现在不能干什么

**这一节比上一节重要。** 说清边界比宣称能力更能建立信任。

### 5.1 六项明确不做（范围冻结时的决定）

| 不做 | 理由 |
|---|---|
| 车辆调度 / 路径优化 | 不在客户一句话需求内；属 TMS 范畴，市面成熟 |
| WMS / 仓储系统对接 | 客户 WMS 是另一家供应商，接口谈判需 6 周以上，超工期 |
| 财务结算 / 理赔计算 | 定责是起点不是终点，赔付金额需法务与商务介入 |
| 司机 App | 需硬件采购 + 司机培训，10 周内无法落地推广 |
| 硬件改造（换记录仪/加探头） | 采购周期 8 周，超工期 |
| AI 温度预测 | 单客户数据量不足以训练，且预测错误的责任无法界定 |

### 5.2 五项技术限制（真相）

| 限制 | 影响 | 严重度 |
|---|---|---|
| **判定规则未经真实业务校准** | 阈值（2.0℃/h、45 分钟、60 分钟）来自行业惯例，非冷鲜通实际规范。可能判得"技术上对、业务上不符" | **高** |
| **单探头假设** | 真实冷藏车 2–3 个探头，多点冲突时如何裁决（取最大/平均/按位置加权）完全未实现 | **高** |
| **无鉴权** | 任何人拿到 URL 都能访问内部视图（含司机姓名、设备编号、车牌） | **高** |
| **SSE 的"实时"是模拟的** | `handleStream` 里的波动由 `Math.sin(tick/3)*0.15` 生成，不是真实设备读数 | 中 |
| **性能未压测** | 68 车×一年量级、并发写入（SQLite 单写锁）未验证。当前估算基于 12 票数据 | 中 |

### 5.3 两处必须找客户确认的

1. **责任判定规则的业务口径**——尤其是 R02（预冷不足）与 R07（制冷能力不足）的分界。这两条在技术上已能区分（是否回落），但"多快算快""回落多少算回落"必须用冷鲜通的历史理赔案例校准。

2. **对外可见字段范围**——当前脱敏剥离了司机姓名、设备编号、完整车牌。但客户可能希望看到车牌（用于自己核对车辆），这需要商务确认。

## 六、数据边界声明

### 6.1 全部数据为虚构

- 客户「冷鲜通冷链」及其 210 人、68 台车、1.4 亿营收等背景，均为**依据一句话需求反推**，不是真实企业信息。
- 12 票运单、司机姓名、车牌、设备编号全部虚构。
- 温度读数由物理模型生成（制冷周期正弦波动 + 开门线性升温 + 停机指数趋近 + 货物带热指数衰减），**非真实记录仪数据**。
- 无任何真实客户数据、真实账号、真实凭据。

### 6.2 推断标注

`docs/02-客户背景.md` 文末有逐项标注表，区分：
- **给定**：来自任务书原文（客户一句话、预算 120 万、10 周）
- **推断**：依据行业常识反推（企业规模、车辆数、温区类型）
- **虚构**：为演示需要编造（具体运单号、人名、车牌）

### 6.3 数据可复现

所有随机数据使用固定种子（mulberry32），同一个种子必然生成同一份数据。删库重跑 `node scripts/seed.js` 得到完全相同的 12 票运单与全部读数。

## 八、关键设计决策速查

被问"为什么这么做"时，答案在这里：

| 问题 | 答案 | 详细位置 |
|---|---|---|
| 为什么零依赖不用框架？ | 评委必须 `node src/server.js` 直接跑起来。多一步 `npm install` 就多一次失败可能 | `docs/04` §1.2 |
| 为什么规则存成数组不写 if-else？ | 业务方要能加规则。数据结构可增删不改引擎 | `docs/04` §2.1 |
| 为什么 R10「无法判定」放最后而不是默认归承运方？ | 默认归责是最常见的产品设计错误——它让系统在证据不足时假装有结论 | `docs/03` + `docs/04` §4.6 |
| 为什么在途运单不判责？ | 货还在路上就出结论等于提前定罪；且技术上必然出错（后续可能恢复） | `docs/04` §4.7 |
| 为什么免责结论需要三重判据？ | 用 12 个点给一整趟运输背书是安全漏洞。**免责的举证责任必须高于归责** | `docs/05` §3.2 |
| 为什么内外用同一个判定函数？ | 防"内部说承运方、客服说收货方、客户把截图发群里" | `docs/04` §5.2 |
| 为什么手写 SVG 不用图表库？ | 需要把超温区间和曲线精确对齐标注；且生成的 DOM 能被 E2E 直接断言 | `docs/04` §6.2 |
| 为什么改物理模型而不是调阈值？ | 规则分不开的两件事，说明领域模型没建对。调阈值只能左右搬分界线 | `docs/05` §3.3 |
| 为什么 Gate 首轮通过率只有 67% 还照实报？ | 改成 100% 很容易（拆指标/改口径），但那样指标就失去牵引作用 | `transform/gates/04` §8 |

## 十、一句话总结

> 这套系统把冷链纠纷里靠吵架解决的责任认定，变成了 **10 条可编号、可测试、可解释、可版本化的规则**，并且用 44 项自动化测试 + 10 项真值校验证明了它按设计工作。
>
> 它现在最大的价值不是"判得准"，而是**"判得清"**——每一条结论都能指到具体规则和具体证据，客户不服可以逐条质询。这正是冷鲜通愿意付 120 万的原因：他们要的不是一个更漂亮的温度看板，是一个能拿去谈判的东西。
