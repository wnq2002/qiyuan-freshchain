# 01 · 现状诊断与范围冻结

> 交付方：启元软件 · 首个场景网格（FDE：总经理兼任）
> 客户：冷鲜通冷链（教学虚构）
> 阶段：诊断（五阶段流水线第 1 段）
> 本文档是范围决策的唯一依据，后续设计与实现不得越出本文冻结的边界。

---

## 一、客户那句话里藏了什么

客户原话：

> "给我做一个能实时看住冷链、出了事能说清是谁的责任、客户问起来能马上回答的系统。预算 120 万，10 周上线。"

一句话里有 **三个不同的能力簇**，且难度极不平均。拆开看：

| 客户原话 | 表面诉求 | 真实问题 | 行业现状 | 难度 |
|---|---|---|---|---|
| "实时看住冷链" | 温度监控看板 | 数据采集与阈值告警 | **商品化能力**，市面成熟产品多 | 低 |
| "说清是谁的责任" | 纠纷定责 | 多主体责任边界的**证据链还原** | 靠人吵、靠微信截图、靠赔付了事 | **高** |
| "客户问起来马上回答" | 客户查询入口 | 对同一份证据的**对外表达能力** | 客服翻记录、口头解释 | 中 |

**诊断结论一：客户买的是"定责"，不是"监控"。**
监控是入口，定责是价值点。如果只做温度看板，等于交了一个淘宝能买到的温湿度记录仪后台，120 万花得没有理由。冷链纠纷的真实成本不在"不知道超温了"，而在"超温了之后三方扯皮两个月、赔了钱还不知道该谁赔、同一个客户下次还问同样的问题"。

**诊断结论二：三个能力不是三个系统，是一份数据的三个视角。**
"看得住"（内部质控视角）、"说得清"（定责视角）、"答得快"（客户视角）必须共用同一条温度序列 + 同一套判定规则。如果做成三个模块各存一份数据，就会出现"看板显示超温 12 分钟、给客户的报告写 8 分钟"的自相矛盾——这正是任务书要求「业务记录与展示结果一致」要防的坑。

**诊断结论三：定责的难点不是算法，是把行业惯例写成可判定规则。**
冷链定责在行业里靠老师傅的经验：看装车温度、看有没有开门、看机组有没有停、看卸货拖了多久。这些经验可以完全形式化为**带编号的规则集**，一旦编号化，就同时获得了三个能力：可测试、可向客户解释、可版本迭代。这是本项目的技术主线。

## 二、现状与差距（启元 + 冷鲜通双视角）

### 2.1 冷鲜通侧

| 维度 | 现状（推断） | 差距 |
|---|---|---|
| 温度采集 | 车载记录仪有，但数据落地在设备厂商平台，导出要申请 | 无法实时、无法与运单关联 |
| 运单管理 | 纸质单据 + Excel 台账 | 温度与运单无关联键 |
| 异常处置 | 司机电话报备，调度手工记录 | 无时间戳、无证据固化 |
| 纠纷处理 | 三方各执一词，靠赔付协商 | 无判定依据、无历史可比 |
| 客户问询 | 客服人工查、口头答 | 响应慢、口径不一、无留痕 |

### 2.2 启元侧（转型前，L1）

与《启元软件 AI Native 转型设计》一致：AI 覆盖率 20%、Token 散落个人账号、无代码库无 Agent 库、SOP 面向人写。**本项目既是客户交付，也是转型的第一个验证样本**——因此交付物中必须同时存在"系统"与"生产这个系统的组织资产"两套东西，缺一不可（详见 `transform/`）。

## 三、预算与工期的真实约束

预算 120 万、工期 10 周。按启元现有成本结构测算：

| 项 | 传统四团队模式 | FDE + Agent 团队 | 说明 |
|---|---|---|---|
| 产品 | 0.5 人月 | 0（并入 FDE） | 需求深访 + MoSCoW 冻结 |
| Coding | 3.0 人月 | 1.5 人月（Agent 产出 + FDE 验收） | 后端/前端/规则引擎 |
| 质检 | 1.5 人月 | 0.5 人月（Agent 出测试 + FDE 判 Gate） | 四层测试 |
| 项目管理 | 1.0 人月 | 0（并入 FDE） | 编排即管理 |
| **合计** | **6.0 人月** | **2.0 人月 + FDE 2.5 人月** | 折合 4.5 人月当量 |

**关键判断：这个项目不缺预算，缺的是 10 周。**
120 万对应 4.5 人月当量的直接人力成本（约 13.5 万）+ 物联网联调（约 8 万）+ 云资源与 Token（约 3 万），毛利空间充裕。因此范围决策的第一约束**不是"钱够不够"，而是"10 周内能不能做完并验证完"**。

由此得出范围决策的判定准则（三条，按优先级）：

1. **能在 10 周内被验证的，才进本期**——不能验证的功能等于没做。
2. **直接支撑"定责"的，优先于"监控得更全"的**——价值密度排序。
3. **依赖客户侧配合（硬件改造、第三方系统对接）的，一律出本期**——不可控依赖是工期杀手。

## 四、范围冻结（本期做 / 不做）

### 4.1 本期交付（P0，三个能力簇）

| # | 能力 | 业务价值 | 验收口径 |
|---|---|---|---|
| C1 | **在途温度实时监控** | 从"事后知道"到"当场知道"，异常响应从小时级降到分钟级 | 看板可查看在途运单温度曲线与告警；温度序列与运单一一关联 |
| C2 | **责任判定证据链** | 纠纷从"三方扯皮"到"规则出结论 + 证据可查"，赔付周期可压缩 | 每票异常运单输出：责任主体 + 判定规则编号 + 证据项 + 置信度；同一输入判定结果恒定 |
| C3 | **客户问询应答** | 客服从"翻记录"到"一键出报告"，同一客户问十次口径一致 | 按运单号查询，输出与内部看板**同源同值**的结论与曲线 |

### 4.2 明确不做（并在答辩时主动说明）

| 不做项 | 理由 |
|---|---|
| 车辆调度 / 路径优化 | 与"定责"无关，且冷鲜通已有 TMS，重复建设 |
| 仓储 WMS / 库内温控 | 属另一系统边界，本期只做"在途" |
| 财务结算 / 赔付流程审批 | 定责结论可对接，但流程引擎不在 10 周范围 |
| 司机端 App / 小程序 | 增加终端与合规成本，本期用网页端覆盖质控与客服两类角色 |
| 温控硬件改造 / 传感器选型 | 依赖客户与设备厂商，用**模拟数据源 + 标准接入契约**替代，边界见 §5 |
| AI 预测性制冷 / 能耗优化 | 数据量不足（需 ≥1 年历史），本期只做确定性规则 |

**不做不是省事，是把工期押在价值最高的地方。** 上面 6 项若全部纳入，10 周必然烂尾；砍掉之后，C1/C2/C3 是一个能被完整验证的闭环。

## 五、虚构数据的边界声明（必须说清）

本项目按任务书要求使用教学虚构数据，边界如下：

| 项 | 做法 | 边界 |
|---|---|---|
| 温度数据 | 物理模型生成（制冷周期波动 + 开门跃升 + 机组故障升温），非真实采集 | 数据形态与真实记录仪一致，但**不接真实设备** |
| 设备接入 | 定义标准接入契约（HTTP 上报 + MQTT 预留），提供模拟上报器 | 真实对接需设备厂商开放协议，属实施阶段工作 |
| 客户与运单 | 全部虚构主体与单号 | 不含任何真实客户信息 |
| 责任判定 | 基于行业惯例形式化的规则集 | 规则可配置、可增删；**不构成法律意见**，正式使用需客户法务确认口径 |

## 六、10 周实施路线（本期按此排期）

| 周 | 里程碑 | 出口 Gate |
|---|---|---|
| W1 | 需求深访 + MoSCoW 冻结 + 数据接入契约 | 需求基线签字 |
| W2 | 领域模型 + 判定规则集 V1（评审会） | 规则集可被业务方逐条读懂 |
| W3–W4 | 温度引擎 + 规则引擎（含单测） | 规则单测覆盖每条规则正/反例 |
| W5–W6 | 后端 API + 质控看板 | 看板数字可回溯到 DB |
| W7 | 客户问询页 + 报告输出 | 内外同源同值 |
| W8 | 集成测试 + 性能 + 悲观 Gate | 覆盖率达标、P0 缺陷清零 |
| W9 | UAT + 数据校准 | 客户业务方走通 3 个真实场景 |
| W10 | 上线 + 交付文档 + 复盘蒸馏 | 冒烟 ≤30 分钟、资产入库 |

本次考核压缩在 180 分钟内，**按同一套五阶段流水线跑通最小可验证闭环**，排期表同样冻结在仓库中，作为后续实施的依据。
