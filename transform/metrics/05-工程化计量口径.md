# 05 工程化计量口径

> **计量口径的价值不在于数字好看，而在于数字不能被操纵。**
>
> 转型方案给了三个硬指标：AI 覆盖率 20%→70%、人均项目数 0.4→1、Token 穿透率 ≥50%。
> 这三个词如果不定义清楚，年底一定变成"各人按自己的理解报数"。本文给出**唯一口径**，并明确"如何能被作弊"。

---

## 一、AI 覆盖率

### 1.1 定义

> **AI 覆盖率 = AI 参与产出的工作量 / 总工作量**
>
> 计量单位：**有效产出工时**（不是日历工时）

### 1.2 什么算"AI 参与"

必须同时满足两个条件：

| 条件 | 判据 |
|---|---|
| ① AI 产出了初稿 | 该产出的第一版由 Agent 生成，不是人先写再让 AI 改 |
| ② 人做了实质性审改 | 人对初稿有修改（改架构/改参数/否掉重做均算），而不是原样采纳 |

**两条都要满足。** 只有 ① 是"AI 生成但没人审"（质量风险）；只有 ② 是"人写完让 AI 润色"（不算 AI 参与）。

### 1.3 什么不算

| 情形 | 为什么不算 |
|---|---|
| AI 补全了一行 `console.log` | 工作量可忽略，计入会虚高 |
| 用 AI 查语法但代码自己写 | AI 是搜索引擎，不是产出者 |
| AI 生成的代码被全部推翻重写 | 实际产出是人做的 |
| 用 AI 写周报 | 不属于项目产出 |

### 1.4 怎么算（可操作）

按**产出物**逐项判定，不按时间：

```
一个交付物（如"判定引擎 288 行"）
  ├─ 初稿由 Agent 生成？          是 → 进入下一步；否 → 计为人
  ├─ 人审改量 > 20%？             是 → 计为 AI 参与；否 → 计为人（AI 基本直接可用，工作量小）
  └─ 人在其中投入的有效工时 = X
```

**AI 覆盖率 = Σ(AI 参与产出物的有效工时) / Σ(全部产出物的有效工时)**

### 1.5 冷鲜通项目实测

| 产出物 | 有效工时 | AI 参与 | 说明 |
|---|---|---|---|
| `docs/01` 诊断 | 1.5h | 否 | 范围判断必须人做 |
| `docs/03` 需求基线 + R01–R10 | 2.5h | 是 | Agent 生成规则初稿，人加了"必须绑作业阶段"等约束 |
| `src/domain/*` 判定引擎 | 3.0h | 是 | Agent 生成，人排查出 6 个缺陷并定修复方向 |
| `src/server.js` 接口层 | 1.5h | 是 | Agent 生成，人定"同源同值"架构 |
| `src/public/*` 前端 | 1.5h | 是 | Agent 生成，人定设计红线 |
| `tests/*` 四层测试 | 2.0h | 是 | Agent 写断言，人设真值 |
| `docs/04` `docs/05` 文档 | 2.5h | 是 | Agent 生成，人补缺陷复盘与边界 |
| Gate 判定与验收 | 2.0h | 否 | 必须是人的判断 |
| **合计** | **16.5h** | **13.5h / 16.5h** | **≈ 82%** |

**本项目 AI 覆盖率 82%**，高于 70% 目标。

**为什么这么高**：因为这是"首个场景网格"，FDE 只有 1 人，几乎所有执行都必须交给 Agent。如果换成 5 人团队按传统方式做，AI 覆盖率会低很多（人各有习惯）。

**所以 82% 不能外推为"公司整体已达 82%"。** 单项目极端值不是组织水平。这也是为什么转型方案的目标是 70% 而不是 82%。

### 1.6 这个指标怎么被作弊

| 作弊方式 | 防线 |
|---|---|
| 把"AI 润色"算成 AI 参与 | 定义要求"初稿由 AI 生成" |
| 只统计代码不统计文档 | 口径明确含文档（文档是交付物） |
| 人先写 AI 后改，算 AI | 定义要求"第一版由 AI 生成" |
| 只报高覆盖项目 | 按项目加权平均，不是简单平均 |

## 二、Token 穿透率

### 2.1 定义

> **Token 穿透率 = 可归属到具体项目/环节的 Token 消耗 / 总 Token 消耗**
>
> 目标：≥50%

### 2.2 "穿透"是什么意思

启元 L1 现状是"Token 支出散落在个人账号，月均约 8000 元，无法按项目/部门归集"。**穿透 = 能追到"这笔钱花在哪个项目的哪个环节"。**

三层可达性：

| 层级 | 能做到什么 | 是否算穿透 |
|---|---|---|
| L0 不可归集 | 只知道本月总花费 8000 元 | 否 |
| L1 归到人 | 知道"张三花了 500 元" | 否 |
| L2 归到项目 | 知道"冷鲜通项目花了 3200 元" | **是（下限）** |
| L3 归到环节 | 知道"冷鲜通项目 S2 阶段规则形式化花了 800 元" | 是（理想） |

**目标 ≥50% 指 L2 及以上占比。**

### 2.3 实现机制（技术方案）

```
统一网关：所有模型调用经内部代理，强制带 project_id / stage 标签
     ↓
计量入库：每次调用记录 {project_id, stage, agent_id, model, in_tokens, out_tokens, cost}
     ↓
周报自动出：按项目/阶段/Agent 汇总
```

**关键约束**：**不允许绕过网关直连模型服务。** 一旦允许，穿透率立刻归零（因为直连的调用无法归集）。这是制度问题不是技术问题。

### 2.4 冷鲜通项目的 Token 归集

| 环节 | 可归集 |
|---|---|
| S1 诊断 | ✅ 按 stage=S1 打标 |
| S2 需求与规则 | ✅ stage=S2 |
| S3 实现 | ✅ stage=S3 |
| S4 验证 | ✅ stage=S4 |
| S5 交付 | ✅ stage=S5 |

**本项目实际达到 L3（可归到环节）**，因为单项目单 FDE，所有调用都在同一上下文。

**但同样不能外推**：单项目天然容易归集（只有一个项目）。多项目并行时，同一 FDE 在同一会话里切换项目，标签就会混乱。**这才是真实难点。**

### 2.5 这个指标怎么被作弊

| 作弊方式 | 防线 |
|---|---|
| 只统计走网关的调用，直连的忽略不计 | 分母必须含"应付全部调用"（按席位×月估算） |
| 把个人订阅费不计入 | 分母含所有 AI 相关支出（含个人账号报销） |
| 归到部门而非项目 | 口径要求 L2（项目级）才计 |

**最狠的一条防线**：分母用"按席位估算的应消耗"而非"实际记录的消耗"。如果实际记录远小于应付估算，说明有大量绕过网关的调用 —— 穿透率应该被**调低**而不是按记录数算高。

## 三、人均项目数

### 3.1 定义

> **人均项目数 = 在途项目数 / 交付人数**
>
> 目标：0.4 → 1（6 个月）→ 3+（18 个月）

### 3.2 三个必须定义清楚的点

**① "在途项目"的边界**

一个项目从 Gate 0 通过到 Gate 5 通过，全程计入在途。**验收后 6 个月的维护期不计入**（否则维护项目多的年份人均数虚高）。

**② "交付人数"的边界**

| 计入 | 不计入 |
|---|---|
| FDE | 纯管理岗 |
| Agent 运营（按 50% 折算，因为一半时间在维护不直接交付） | 销售、财务 |
| 领域专家（按实际投入折算） | 实习生 |
| 平台/基础设施（按 30% 折算） | 外包（单独统计） |

**折算规则要事先定死**，否则年底必然扯皮。

**③ 分母用"人"还是"人月"**

用**人**（FTE 折算）。理由：转型目标是"1 人带 1 项目"，用人月算会把"兼职参与"也算进去，失去意义。

### 3.3 冷鲜通项目的折算

| 项 | 数 |
|---|---|
| 在途项目 | 1（冷鲜通） |
| 交付人数 | FDE 1 人（100%）+ Agent 运营 0.5 折算 + 领域专家 0.2 折算 = 1.7 |
| **人均项目数** | **1 / 1.7 = 0.59** |

**注意**：单项目的人均项目数没有统计意义（1 个项目最多就是 1/1=1）。这个指标必须在**部门级（≥5 个项目）**才有意义。

**所以冷鲜通项目只能证明"1 个 FDE 能带 1 个项目"，不能证明"人均项目数达到 1"。** 后者需要 6 个月、多项目并行才能验证。

### 3.4 这个指标怎么被作弊

| 作弊方式 | 防线 |
|---|---|
| 把大项目拆成多个小项目立项 | 项目定义：独立的客户合同/独立验收 |
| 把维护期项目计入在途 | 明确要求 Gate 0–5 之间 |
| 减少分母（只算 FDE 不算支撑） | 折算规则事先定死并公示 |
| 接一堆不做的小项目 | 配套指标：项目平均金额不得下降 |

## 四、辅助指标（防止主指标失真）

三个主指标都可能被单点优化。以下四个辅助指标用来交叉验证：

| 指标 | 定义 | 防什么 |
|---|---|---|
| **Gate 首轮通过率** | 首轮通过 Gate 数 / 总 Gate 数 | 防"为了快而降低质量" |
| **上线首月缺陷数** | 交付后 30 天内的生产缺陷 | 防"AI 生成但没人审" |
| **新人达标天数** | 新人达到老人 80% 产出的天数 | 防"资产库建了没用" |
| **FDE 工时 A+B 占比** | (定义+验收) / 总工时 | 防"FDE 退化成 AI 操作员" |

### 4.1 为什么必须有 FDE 工时 A+B 占比

这是唯一能直接反映"转型方向对不对"的指标。

如果 AI 覆盖率上去了（70%）、人均项目数上去了（1），但 FDE 的 A+B 占比从 65% 掉到 25% —— 说明 FDE 变成了"调 AI 的人"，而不是"判标准的人"。**这样的转型在数字上成功，在实质上失败。**

判定红线：**A+B ≥ 40%**。低于此值，即使其他指标达标，也要判定该网格转型失败。

### 4.2 冷鲜通项目实测

| 指标 | 实测 | 目标 | 结论 |
|---|---|---|---|
| AI 覆盖率 | 82% | 70% | 达标（单项目极端值，不外推） |
| Token 穿透率 | L3（可归到环节） | ≥50% | 达标（单项目易，多项目难） |
| 人均项目数 | 0.59（无统计意义） | 1 | 不可判定 |
| Gate 首轮通过率 | 67%（4/6） | >90% | **未达标**，如实记录 |
| FDE 工时 A+B | 65% | ≥40% | 达标 |

**五项里两项达标、一项不可判定、一项未达标。** 这个结果比"全部达标"可信。

## 五、计量看板（周报形式）

每周自动出一页，格式固定：

```
┌─────────────────────────────────────────────────────────┐
│ 启元 AI Native 计量周报 · 第 N 周                        │
├─────────────────────────────────────────────────────────┤
│ 主指标                                                  │
│   AI 覆盖率        62%  (↑3)   目标 70%                 │
│   Token 穿透率     58%  (↑2)   目标 50%  ✅             │
│   人均项目数       0.68 (↑.04) 目标 1.0                 │
├─────────────────────────────────────────────────────────┤
│ 辅助指标                                                │
│   Gate 首轮通过率  78%         目标 >90%                │
│   上线首月缺陷     2.1 个/项目 目标 <3                  │
│   新人达标天数     18 天       目标 ≤14                 │
│   FDE 工时 A+B     58%         红线 ≥40%  ✅            │
├─────────────────────────────────────────────────────────┤
│ 异常提示                                                │
│   ⚠ 项目 P-0231 的 Agent 库调用次数为 0，需核查是否复用 │
│   ⚠ FDE 张×× A+B 占比 32%，低于红线                     │
└─────────────────────────────────────────────────────────┘
```

**"异常提示"这一栏是最有用的部分。** 指标本身只是数字，异常提示才是行动项。

**规则**：每周最多 3 条异常提示，按严重度排序。超过 3 条说明指标设定有问题（或组织真的出大问题了），需要人工介入。

## 六、口径变更管理

口径一旦定了，**一年内不得修改**。理由：口径变了，历史数据就不可比，趋势线断掉。

如果确实需要改（比如发现某个定义有漏洞），流程：

1. 写变更说明（为什么改、影响哪些历史数据）
2. 新口径并行统计 3 个月（新旧同时出数）
3. 3 个月后切换，历史数据标注"旧口径"

**不允许的做法**：直接改定义然后重新算历史数据。这等于篡改趋势。

## 七、这一章的三条底线

| 底线 | 内容 |
|---|---|
| **分母不许缩** | 任何指标的分母都取"应付"而非"实付"（防绕过） |
| **单点不外推** | 单项目/单人的极端值不得代表组织水平 |
| **指标不达标照实报** | 67% 就是 67%，不改口径、不拆指标、不修饰措辞 |

第三条最重要。**一个能容下"未达标"的计量体系，才有牵引力。** 如果所有指标永远达标，说明这些指标没在被认真用。
