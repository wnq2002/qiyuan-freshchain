# 03 SOP 2.0：五阶段流水线

> SOP 1.0 写给人看：步骤、责任、时间。
> **SOP 2.0 写给 Agent 看：契约、上下文、验收判定。**
>
> 判据很简单：**一份 SOP 如果是给 Agent 用的，读完之后 Agent 不需要再问人。** 如果还需要问"这一步输出什么格式""做到什么程度算完"，说明 SOP 没写够。

---

## 一、五阶段总览

```
S1 诊断 → S2 需求与规则 → S3 实现 → S4 验证 → S5 交付
   ↓            ↓             ↓          ↓          ↓
范围冻结      规则表+真值    可运行系统   四层测试   交付包
 [Gate1]     [Gate2]       [Gate3]    [Gate4]    [Gate5]
```

**每阶段必须有一次代码仓库提交。** 未提交按未完成处理——这条不是形式要求，是因为"没有提交记录"等于"无法证明过程存在"。

| 阶段 | 输入 | 输出 | Gate | 冷鲜通实际耗时 |
|---|---|---|---|---|
| S1 诊断 | 客户原话、预算工期 | 能力簇拆分 + 不做清单 + 人月测算 | Gate 1 | ~1.5h（9%） |
| S2 需求与规则 | 能力簇、领域经验 | MoSCoW 基线 + 规则表 + 场景真值 | Gate 2 | ~3.5h（21%） |
| S3 实现 | 规则表、接口契约 | 可运行系统 | Gate 3 | ~4.5h（27%） |
| S4 验证 | 系统、真值 | 四层测试 + 缺陷复盘 | Gate 4 | ~3h（18%） |
| S5 交付 | 全部成果 | 交付说明 + 转型落地包 | Gate 5 | ~4h（25%） |

> 耗时占比供参考：**S1+S2 占 30%** 是正常且必须的。如果 S1+S2 只占 10%，说明范围没想清楚，后面必然返工。

## 二、S1 诊断

### 2.1 步骤（Agent 可执行）

| # | 动作 | 产出 |
|---|---|---|
| 1 | 记录客户原话，**逐句拆**成需求点 | 需求点列表 |
| 2 | 对每个需求点判断：是商品化能力还是价值点？ | 能力簇表 |
| 3 | 判定哪个能力簇是客户真正付钱的理由 | 价值点结论（一句话） |
| 4 | 列出本期**不做**什么，每项给理由 | 不做清单 |
| 5 | 估算传统模式 vs 新模式人月 | 测算表 |
| 6 | 声明虚构数据边界 | 边界声明 |

### 2.2 关键约束

**【强制】必须输出"不做清单"，且不少于 3 项。**

理由：范围失控是定制项目的第一死因。转型方案记录的"需求评审 3.4 轮、返工率 22%"，根因不是评审不认真，是范围从未真正冻结过。**写清不做什么，比写清做什么更能锁定范围。**

冷鲜通不做清单 6 项：车辆调度、WMS 对接、财务结算、司机 App、硬件改造、AI 预测。每项都给了理由（如"硬件改造需 8 周采购周期，超出 10 周工期"）。

**【强制】价值点判断必须回答"客户为什么愿意为这个付钱"。**

不能是"提升效率""降本增效"这类无法证伪的话。冷鲜通的答案是：**冷链纠纷的真实成本在"超温后三方扯皮两个月、赔了钱还不知道该谁赔"**。所以客户买的不是监控（淘宝能买），是定责。

### 2.3 Gate 1 检查清单

- [ ] 需求点全部来自客户原话，没有自行添加
- [ ] 能力簇不超过 3 个 P0（超了说明没做取舍）
- [ ] 价值点结论能用一句话说清，且能回答"为什么付钱"
- [ ] 不做清单 ≥3 项，每项有理由
- [ ] 人月测算含传统模式对照
- [ ] 虚构数据边界已声明（哪些是给定的、哪些是推断的、哪些是虚构的）
- [ ] **已提交代码仓库**

## 三、S2 需求与规则

### 3.1 步骤

| # | 动作 | 产出 |
|---|---|---|
| 1 | 模拟需求深访（至少 3 轮），记录客户口语 | 访谈纪要 |
| 2 | 从纪要中提炼隐含需求（客户没说但必须有的） | 隐含需求清单 |
| 3 | 用 MoSCoW 分级 | 需求基线 |
| 4 | 把领域惯例形式化为规则表（编号 + 主体 + 优先级 + 业务含义） | 规则表 |
| 5 | 为每条规则造 1 个验证场景，**并声明期望结论** | 场景库 + 真值 |
| 6 | 跑真值校验，不过则回到第 4 步 | 校验报告 |

### 3.2 关键约束

**【强制】规则存成数据结构，不写成代码分支。**

```js
// 正确
const RULES = [{ id, name, party, priority, test(ctx) }, ...];

// 错误
if (装车温度超标) return '发货方';
else if (开门超时) return '承运方';
```

理由：数据结构可增删不改引擎，业务方能参与；if-else 每次加规则都要改引擎、改测试、重新回归。

**【强制】期望结论必须在造数据时写，不能看到判定结果后补。**

理由：看到结果再写期望，等于把测试变成"确认当前行为"。冷鲜通首轮 4/10 之所以有价值，正是因为期望是先写的。

**【强制】规则涉及作业行为时，必须绑定时间域。**

踩坑记录：R03「途中开门超时」最初只判断 `door_open && duration > 10`，把卸货时开门 140 分钟判成了"承运方途中私自开门"——**责任方判反**。修复是加 `depart ≤ open < arrive` 约束。

### 3.3 需求深访要问出的东西

冷鲜通项目在第 2 轮访谈才问出关键结论：

> **"定责不是事后裁判，是过程归因。"**

这句话改变整个设计：如果只是事后裁判，只需要最终温度 + 最后结论；因为是过程归因，必须有完整的事件时间轴（何时出发、何时开门、何时停机、何时到达），才能把责任落到具体作业环节。

**这类结论不可能从需求文档里读到，只能从深访里问出来。** 所以 SOP 强制"至少 3 轮"，第 1 轮通常只能问到表面诉求。

### 3.4 Gate 2 检查清单

- [ ] 需求深访 ≥3 轮，有纪要
- [ ] 隐含需求已提炼（客户没说的）
- [ ] MoSCoW 分级完成，Must 项有验收标准
- [ ] 规则表：每条有编号/名称/责任主体/优先级/业务含义
- [ ] 规则优先级唯一，且有短路求值顺序说明
- [ ] 每条规则至少 1 个验证场景，且**期望结论先写**
- [ ] 真值校验通过率 100%（冷鲜通首轮仅 40%，修复后 100%）
- [ ] 遗留问题如实记录（阈值未校准、样本单一等）
- [ ] **已提交代码仓库**

## 四、S3 实现

### 4.1 步骤

| # | 动作 | 产出 |
|---|---|---|
| 1 | 定技术栈，写清选型理由与被否决方案 | 技术决策记录 |
| 2 | 定模块边界（哪两个模块必须分开，为什么） | 架构图 + 边界说明 |
| 3 | 定数据模型（每张表为什么这么设计） | Schema + 设计理由 |
| 4 | 定接口契约（路径/入参/出参/错误码） | 接口表 |
| 5 | 实现领域层（先跑通真值校验） | domain 代码 |
| 6 | 实现接口层 | server 代码 |
| 7 | 实现前端（能真实渲染） | public 代码 |

### 4.2 关键约束

**【强制】技术选型必须写"被否决的替代方案"及否决理由。**

理由：只写"我用了 A"，读者无法判断这是深思还是随手。写清"为什么不用 B"，才能看出取舍。冷鲜通选零依赖 Node，否决了 Express（评委多一步 npm install 就可能失败）、PostgreSQL（要装服务）、Chart.js（难以精确标注证据区间）。

**【强制】模块边界必须说清"如果合并会怎样"。**

冷鲜通把 `rules.js`（判断层）和 `analyze.js`（事实层）分开，理由：合并后加第 11 条规则要改引擎、改测试、改接口；分开后只加一个数组元素。**这是让业务方能参与规则维护的前提。**

**【强制】同源同值：对外视图必须复用内部分析函数，不得另写一套。**

```js
// 内部
const d = analyzeWaybill(no); return d.verdict;
// 对外
const d = analyzeWaybill(no); return toPublic(d);   // 同一个 d，只裁剪字段
```

理由：冷链行业最常翻的车是"内部说承运方责任，客服系统说收货方责任，客户把两张截图发群里"。必须从架构上消除这种可能，而不是靠流程约束。

**【强制】数据必须可复现。**

固定种子伪随机（mulberry32），不用 `Math.random()`。理由：数据不可复现，验证结论就不可复现。

### 4.3 Gate 3 检查清单

- [ ] 技术选型有理由 + 否决方案
- [ ] 模块边界有"合并会怎样"的说明
- [ ] 数据模型每张表有设计理由
- [ ] 接口契约完整（含错误码）
- [ ] 领域层通过真值校验
- [ ] 内外视图同源同值（代码层面就是同一个函数）
- [ ] 数据可复现（固定种子）
- [ ] 服务能零依赖启动（或明确写出安装步骤且测试过）
- [ ] **已提交代码仓库**

## 五、S4 验证

### 5.1 步骤

| # | 动作 | 产出 |
|---|---|---|
| 1 | 写 L1 真值校验（若 S2 已写则复用） | 校验脚本 |
| 2 | 写 L2 单元测试（每个纯函数至少 2 个断言：正常 + 边界） | 单测 |
| 3 | 写 L3 集成测试（真实 HTTP，含一致性 + 脱敏断言） | 集成测试 |
| 4 | 写 L4 端到端（真实浏览器渲染 DOM） | E2E 测试 |
| 5 | 测性能（关键路径耗时 + 索引执行计划） | 性能数据 |
| 6 | 写缺陷复盘（每个缺陷：现象/根因/修复/教训） | 缺陷记录 |
| 7 | 写"不能证明什么" | 边界声明 |

### 5.2 关键约束

**【强制】四层测试不可省任一层，且每层至少一个业务语义断言。**

只断言状态码 200 的测试是假测试——一个把所有运单都判成"无责任方"的系统也能通过。

**【强制】E2E 必须渲染真实 DOM，不得只测接口。**

理由：前端 JS 报错、曲线画不出来、模板渲染失败，接口测试全绿，客户打开是白屏。

**【强制】脱敏测试用字符串黑名单，不用字段名白名单。**

```js
// 正确：直接搜真实敏感值
assert.ok(!body.includes('陆文斌') && !body.includes('RC-2023-0460'));

// 错误：检查有没有某字段名（字段名一改就失效）
assert.equal(body.driver, undefined);
```

**【强制】缺陷复盘必须写"教训"，不能只写"已修复"。**

冷鲜通 8 条缺陷复盘中，最有价值的是 R08 那条：

> 用 12 个点给一整趟运输背书。首次修复加 `readings >= 10` 条数下限，被 12 条读数绕过。
> 教训：**免责结论的举证责任必须高于归责结论。** 归责可用排除法，免责必须完整证据。

**【强制】"不能证明什么"不得少于 3 条。**

只能证明自己的系统处处都好，这个报告不可信。冷鲜通列了 7 条（阈值未校准、单探头、性能未压测、SSE 是模拟、无鉴权等）。

### 5.3 Gate 4 检查清单

- [ ] L1 真值校验通过（冷鲜通 10/10）
- [ ] L2 单测覆盖所有纯函数，含容差/去抖/边界
- [ ] L3 集成含同源同值断言 + 脱敏黑名单断言
- [ ] L4 E2E 真实渲染 DOM
- [ ] 性能有实测数字，不是估算
- [ ] 缺陷复盘含根因 + 教训
- [ ] "不能证明"≥3 条
- [ ] 复现命令实际跑过
- [ ] **已提交代码仓库**

## 六、S5 交付

### 6.1 步骤

| # | 动作 | 产出 |
|---|---|---|
| 1 | 写运行说明（零依赖/依赖、命令、端口） | README |
| 2 | 写使用说明（三条角色路径 + 演示脚本） | 交付说明 |
| 3 | 写边界与未解决问题 | 边界声明 |
| 4 | 整理资产（代码库六项完整度自检） | 资产清单 |
| 5 | 写转型落地包（组织/Agent/SOP/Gate/计量） | transform/ |
| 6 | 全部推送到仓库，验证远程可访问 | 提交记录 |

### 6.2 关键约束

**【强制】运行说明必须"从零可复现"：假设读者只有一台干净电脑。**

冷鲜通的做法：`node scripts/seed.js && node src/server.js`，无需 `npm install`、无需数据库服务、无需联网。

**【强制】演示路径必须固定，且每条都跑到结论。**

冷鲜通三条路径：
1. 质控：看板 → 看到 4 票严重告警置顶 → 点进 006 → 看到 R05 证据链
2. 客服：客户问询 → 输 003 → 拿到「发货方 · 预冷不足」→ 与内部详情页比对数值一致
3. 质疑：规则页 → 看到 R01–R10 全部规则与优先级 → 理解判定依据

第 3 条最容易漏，但对**信任**最关键。客户第一反应是"你系统乱判"，把规则摆出来才能对话。

**【强制】代码库六项完整度自检。**

| 项 | 判据 | 冷鲜通状态 |
|---|---|---|
| 目录结构 | 有清晰的 docs/src/tests/gates/transform 分层 | ✅ |
| README | 5 分钟能跑起来 | ✅ |
| 版本管理 | 每阶段一次提交，信息说清做了什么 | ✅ 5 次提交 |
| Agent 上下文 | 关键约束写进 Agent 可读位置 | ✅ transform/agents |
| 可复制 SOP | 换人照做结果一致 | ✅ transform/sop |
| 不因人而异 | 决策理由全部落在文档里，不在人脑里 | ✅ 设计文档含取舍记录 |

### 6.3 Gate 5 检查清单

- [ ] 未解决问题如实列出

- [ ] 转型落地包完成（5 个文件）
- [ ] 仓库已推送且远程可访问

## 七、五阶段之外：这个 SOP 怎么被改进

SOP 本身也要迭代。机制是：**每个项目的缺陷复盘，必须回写到这里**。

冷鲜通已经回写了 3 条到本 SOP：

| 回写内容 | 位置 |
|---|---|
| 规则必须绑定作业阶段 | §3.2 强制约束 |
| 免责结论举证责任高于归责 | §5.2 强制约束 |
| 规则分不开就改模型不改阈值 | §5.2 强制约束 |

**所以 SOP 2.0 是有版本的活文档，不是一次性写好的规范。** 版本号规则：加一条强制约束 = minor，改阶段划分 = major。
