# 启元软件 AI Native 转型落地包

> 12 个月 L1 → L3 的可执行资产。不是方法论，是**换个人也能跑出同样结果**的操作物。
> 全部内容来自冷鲜通项目（首个场景网格）的真实执行经验，含踩坑记录。

---

## 一、这个包要解决什么

转型方案里最容易被写空的一段是"组织形态怎么变"。写"用 FDE + Agent 取代职能接力"很容易，但**第二天上班，一个 58 人的公司具体怎么动**？这个包回答四件事：

| 问题 | 答案在哪 |
|---|---|
| 人怎么摆、谁干什么、FDE 一天在做什么 | `01-组织形态与FDE工作法.md` |
| 哪些活交给 Agent，Agent 从哪来、怎么维护 | `agents/02-Agent库.md` |
| 一件活从头到尾的步骤，写成谁都能照着做的规程 | `sop/03-SOP2.0五阶段流水线.md` |
| 每一段怎么判合格、不合格怎么办 | `gates/04-六阶段Gate表.md` |
| AI 用了多少、钱花哪了、人效怎么算 | `metrics/05-工程化计量口径.md` |

## 二、三条贯穿全包的原则

### 原则一：人站两端，Agent 走中间

```
客户需求  →  [FDE：定义标准]  →  Agent 执行  →  [FDE：验收结果]  →  交付
                    ↑                                    ↑
              这一段必须人做                      这一段必须人做
              Agent 做不了：                      Agent 做不了：
              · 判断"客户真正要什么"              · 判断"这是否算合格"
              · 决定"这次不做什么"                · 承担对客户的承诺
```

冷鲜通项目的实证：整个项目我（FDE）实际写代码的时间不到 20%，80% 的时间花在**范围冻结**（做什么/不做什么）和**验证**（判得对不对）上。中间的编码、造数据、写测试、画前端，绝大部分由 Agent 完成。

**这个比例本身就是转型成效的证据**：传统模式下，一个 120 万的定制项目需要产品 1 人 + 开发 3 人 + 测试 1 人 = 5 人 × 2.5 个月 = 12.5 人月。本项目 1 人 × 10 周 = 2.3 人月（含 Agent 编排）。

### 原则二：每段默认不合格，以证据自证合格才放行

这是质量立场，不是流程修辞。具体到操作上：

> 每完成一段，先假设它有问题，然后**主动找证据推翻这个假设**。找不到反面证据，才允许放行。

冷鲜通的实证价值在这里：我第一次跑规则真值校验，**10 个场景只对了 4 个**。如果按"接口返回 200 就算过"的标准，这 10 个场景会全部通过——因为接口确实都返回了结构正确的数据。

**"默认不合格"这个立场，直接决定了我会去建真值校验这套东西。** 没有这个立场，就不会有那 6 个缺陷的发现。

### 原则三：资产化优先于交付优先

每做完一件事，多问一句：**"下次做同类项目，这个能直接用吗？"**

- 规则引擎 → 可复用的"数据驱动规则表"模式
- 12 个场景 → 可复用的"真值校验"验证方法
- 这次踩的 8 个坑 → 写进 Gate 表，下次直接查表
- 判定算法 → 写进 Agent 上下文，Agent 下次自动遵守

**判断标准**：一个新人接手同类项目，读完资产库能不能在两周内达到老人 80% 的产出？达不到，说明资产化没做够。

## 三、从 L1 到 L3 的路径（不是一次性跳跃）

转型方案写"12 个月从 L1 到 L3"。但这个跨度不可能一步到位。实际路径是三级台阶，每一级有明确的**可观测状态**：

### L1（现状）→ L1.5：工具可用

| 维度 | L1 | L1.5 |
|---|---|---|
| AI 覆盖率 | 20% | 40% |
| Token | 散落个人账号，月均 8000 元无法归集 | 统一入口，按项目打标 |
| 代码库 | 无 | 每项目有 README + 目录规范 |
| Agent 库 | 无 | 3–5 个高频 Agent 沉淀 |
| SOP | 面向人写 | 关键环节补 Agent 上下文 |

**判定条件**：随便挑一个项目，能说清"这个项目花了多少 Token、AI 做了哪些环节"。

**冷鲜通项目已达到 L1.5**：本项目有完整的代码库（README/目录/提交记录/Agent 上下文/SOP/不因人而异六项）、判定规则以数据结构形式沉淀、Gate 表可查。

### L1.5 → L2：流程可复制

| 维度 | L2 |
|---|---|
| AI 覆盖率 | 55% |
| 人均项目数 | 0.6 |
| 代码库 | 有跨项目复用层（登录/权限/报表等） |
| Agent 库 | 覆盖本部门主要重复性任务 |
| SOP | 五阶段流水线完整，新人可照做 |

**判定条件**：换一个 FDE 驱动同一套资产库，交付结果一致（差异 <10%）。

### L2 → L3：默认执行单元

| 维度 | L3 目标 |
|---|---|
| AI 覆盖率 | 70%，牵引 90%+ |
| 人均项目数 | 1 |
| 代码库 + Agent 库 | 默认知识资产（不是"有"，是"默认用"） |
| Token / 人均项目数 | 默认计量口径（每周看板自动出） |

**判定条件**：项目立项时，第一反应是"查 Agent 库有没有现成的"，而不是"排人"。

## 四、12 个月落地排期

| 月份 | 阶段 | 关键动作 | 可验证产出 |
|---|---|---|---|
| M1 | 立标杆 | 冷鲜通项目按新流程跑通五阶段 | 代码库 + 本落地包 |
| M2 | 建资产 | 抽 3 个高频 Agent、定 Gate 表、上计量看板 | Agent 库 v1、Token 归集口径 |
| M3 | 小范围复制 | 选 2 个新立项项目用新流程 | 2 个项目报告（AI 覆盖率实测） |
| M4–M6 | 扩面 | 新立项全部走新流程；FDE 认证首批 6 人 | 人均项目数 0.4 → 0.6，AI 覆盖率 40% |
| M7–M9 | 并线 | 并行编排试点；旧流程冻结 | 并行耗时 ≤ 串行 50% |
| M10–M12 | 达 L3 | 存量 23 个项目维持 + 新项目全 AI Native | AI 覆盖率 70%、人均 1、Token 穿透 ≥50% |

**先立后破**：M1–M3 只做"建"，不动旧流程；M4 之后才上"增编红线"和"旧流程冻结"。这是转型方案里明确的节奏约束，落地包必须遵守——否则前 3 个月就会因为新旧并行而全面卡住。

**不裁员不降薪的兑现方式**：M4–M6 通过 FDE 认证把产品/质检/项目管理的人转成 FDE 或 Agent 运营岗；产能提升的红利用于**接更多项目**，而不是减少人头。

## 五、风险与对冲

| 风险 | 触发信号 | 对冲动作 |
|---|---|---|
| **Agent 产出无人验收，质量塌方** | Gate 通过率虚高（>98% 且上线后缺陷上升） | Gate 抽查机制：每 10 个项目随机抽 1 个做全流程复核 |
| **FDE 变成"AI 操作员"** | FDE 时间 80% 花在调 Agent，而非定义标准与验收 | FDE 工时四分法计量（见 `metrics/05`），定义+验收时间占比不得低于 40% |
| **资产库建了没人用** | Agent 库调用次数周环比不增 | 把"是否复用资产"纳入项目验收项；不复用需书面说明理由 |
| **需求频繁变更拖垮流水线** | 需求评审超 3 轮 | 强制 MoSCoW 冻结基线；未冻结不进流水线（冷鲜通项目即按此执行） |
| **Token 成本失控** | 单项目 Token 超预算 150% | 按项目设 Token 额度，超限需 FDE 审批 |
| **老员工抵触** | 认证通过率 <60% | 认证与晋升挂钩但不与薪酬挂钩（首年）；设"AI 协作标兵"内部标杆 |
| **核心开发流失带走隐性知识** | 年流失率 18% 未降 | 资产库硬要求：关键逻辑必须进代码注释 + Agent 上下文，不进脑子 |

## 六、冷鲜通项目作为样本的证明力与局限

### 能证明

1. **1 个 FDE + Agent 能交付 120 万级定制项目**（本项目实际投入 2.3 人月）
2. **五阶段流水线可跑通**，且每阶段有可验证产出（4 个提交记录 + 5 份文档 + 1 份 Gate 报告）
3. **"默认不合格"立场能逼出真问题**（真值校验从 4/10 拉到 10/10，发现 6 个真实缺陷）
4. **资产可沉淀**（规则表、场景库、Gate 表、本落地包）

### 不能证明（必须说清）

1. **一个样本不能证明可复制。** 我熟悉这个业务域，换个陌生领域（比如制造 EHS）FDE 效率会显著下降。
2. **本项目是"绿field"，存量 23 个项目的改造难度完全不同**——老代码没有测试、没有文档、需求方还在改。落地包对存量项目只做了"维持"安排，没有改造方案，这是有意的取舍（转型方案明确"存量不回头改造"）。
3. **AI 覆盖率 70% 是目标不是结果。** 本项目单点的 AI 参与度无法直接外推到全公司。
4. **人均项目数 0.4 → 1 需要 6 个月才可验证**，现在只能给出路径和判定条件，不能给出结论。
