# 04 六阶段 Gate 表

> **质量立场：每段产出默认不合格，以证据自证合格才放行。**
>
> Gate 表不是检查清单，是**放行判据**。区别在于：清单可以"基本做到了"就勾选，判据只有"通过/不通过"。
> 每一项都必须是**可机器判定**或**可在 2 分钟内人工核对**的。

---

## 一、为什么是六段而不是五段

五阶段流水线是 S1–S5，但 Gate 有六个。第六个是 **Gate 0：立项前**。

| Gate | 位置 | 判什么 |
|---|---|---|
| **Gate 0** | 项目启动前 | 这个项目该不该接、该按什么模式接 |
| Gate 1 | S1 诊断后 | 范围是否真的冻结了 |
| Gate 2 | S2 需求与规则后 | 规则是否可测试、真值是否互不知情 |
| Gate 3 | S3 实现后 | 架构边界是否立住了 |
| Gate 4 | S4 验证后 | 证据是否足以自证合格 |
| Gate 5 | S5 交付后 | 换个人能不能复现 |

**Gate 0 的必要性**：转型最容易犯的错是"所有项目都按 AI Native 做"。需求频繁变更、客户不接受范围冻结的项目，硬上流水线会全面卡死。**Gate 0 就是筛掉这类项目。**

## 二、Gate 0：立项前

### 2.1 判据

| # | 判据 | 通过条件 | 不通过怎么办 |
|---|---|---|---|
| 0.1 | 客户能否接受范围冻结 | 客户书面认可"本期不做清单" | 不进流水线，先做需求深访 |
| 0.2 | 需求变更频率 | 历史项目月均变更 ≤2 次 | 改为"小步交付"模式，每 2 周一个可验收片段 |
| 0.3 | 是否有可复用资产 | 代码库命中 ≥1 个模块 | 无命中则预留 20% 工期做首次沉淀 |
| 0.4 | 数据合规边界 | 明确客户数据可用范围与脱敏要求 | 不通过则不接 |
| 0.5 | FDE 带宽 | 该 FDE 在途项目 ≤2 个 | 排队或换人 |

### 2.2 冷鲜通项目实测

| 判据 | 结论 |
|---|---|
| 0.1 范围冻结 | 客户"只给一句话"，需先深访再冻结 → 归入 S1 一并完成 |
| 0.2 变更频率 | 新客户，无历史数据 → 按冻结基线 + 变更需书面申请 |
| 0.3 可复用资产 | 启元有物流 EHS 平台经验，规则引擎模式可迁 → 命中 |
| 0.4 数据合规 | 教学虚构数据，无真实客户信息 → 通过（并声明边界） |
| 0.5 FDE 带宽 | 首个网格，FDE 仅此 1 个项目 → 通过 |

**结果：有条件通过**（0.1 需在 S1 补做，0.2 需建立变更控制）。

### 2.3 Gate 0 的红线

- **客户拒绝冻结范围，且项目预算 <200 万 → 不接。** 理由：小项目没有返工空间，需求不冻结必然亏。
- **数据合规不清 → 不接。** 无例外。
- **同一 FDE 在途超 2 个项目 → 不派。** 理由：FDE 的 A+B 时间会被压缩到 40% 以下，退化成协调员。

| 1.6 | 虚构数据边界 | 逐项标注"给定/推断/虚构" | ✅ `docs/02` 文末标注表 |
| 1.7 | 仓库提交 | 有提交记录 | ✅ `213cd1d` |

### 3.1 最容易作假的一项：1.3 不做清单

"6 项不做"很容易写成凑数的（比如"不做火箭发射"）。**判据要能识别凑数**：

> 每项"不做"必须满足两个条件之一：
> ① 客户可能真的会要求（有商业合理性）
> ② 技术上相关但本期做不了（有明确阻碍）

冷鲜通的 6 项全部满足：车辆调度（客户确实会想要）、WMS 对接（客户有 WMS）、财务结算（相关）、司机 App（相关，但需硬件+培训）、硬件改造（8 周采购超期）、AI 预测（样本量不足）。

**凑数项的反例**："不做区块链""不做元宇宙"——客户不会要求，删掉。

### 4.1 2.6「真值先写」怎么核查

这是最容易被绕过的一项。**核查方法：看 git 历史。**

```bash
git log --follow -p src/domain/scenarios.js | grep "expect:"
```

如果 `expect` 与判定逻辑在**同一次提交**里被同时修改，就有"看到结果改期望"的嫌疑。合规的做法是：期望写在规则实现之前，或至少在同一次提交中但由不同 Agent 产出。

冷鲜通的做法：`scenarios.js`（含 expect）与 `rules.js` 在同一次提交，但 expect 是我（FDE）手写的，规则是 Agent 实现的，两边不通信。**这一点只能靠过程纪律保证，Gate 无法自动判定 —— 如实说明。**

### 4.2 首轮 40% 的处理方式

**Gate 2 首轮不通过。** 处理流程：

1. 不降低标准（不把"通过率 40%"当合格）
2. 逐条查失败原因，区分"规则写错"与"模型太粗"
3. 修复后重跑，直到 100%
4. **把每个缺陷写进复盘**（`gates/gate-02-规则引擎验证.md` 记了 6 个）

**关键**：Gate 不通过不是坏事，掩盖不通过才是。如果首轮就 100%，反而要怀疑真值是不是后补的。

### 5.1 3.5 同源同值的核查方法

**不看文档，看代码。**

```bash
grep -n "analyzeWaybill(no)" src/server.js
```

如果 `/api/track` 和 `/api/waybills/:no/judgement` 两个 handler 里出现**同一个函数调用**，且对外只多一层 `toPublic()` 裁剪，就是同源同值。

如果出现两个不同的分析函数（比如 `analyzeForCustomer` 和 `analyzeForInternal`），**直接判不通过**——这是架构层面的翻车隐患，靠测试兜不住。

### 6.1 4.2 各层的业务语义断言（冷鲜通实例）

| 层 | 假测试（不通过） | 真断言（通过） |
|---|---|---|
| L1 | 校验脚本返回 0 | 10 个场景期望与实际逐条比对，全部一致 |
| L2 | `expect(sum).toBeDefined()` | 容差内 2.4℃ 不算超温；超容差 2.6℃ 算超温 |
| L3 | `expect(res.status).toBe(200)` | 内外结论 `ruleId/partyName/detail` 逐项相等 |
| L4 | `expect(html).toContain('<div')` | SVG 路径 `split('L').length > 50`，且含"预冷不足""发货方""证据链" |

### 6.2 4.7 为什么"不能证明"必须≥3 条

因为**任何一份只能证明自己处处合格的验证报告，可信度都低于一份敢说边界的报告**。

如果一份报告写"全部通过，无遗留问题"，评审的第一反应应该是：他没认真测。

冷鲜通的 7 条不能证明中，最要紧的是第 1 条：

> 判定规则对不对，只在我的虚构场景上验证过。场景是我造的，真值是我定的。10/10 只说明"引擎按我的设计工作"，不说明"我的设计符合真实业务"。

**这条自陈比 10/10 更有价值**，因为它指出了这个交付真实的成熟度边界。

## 八、Gate 通过率统计方式

转型方案要求"各段质量 Gate 通过率 >90%"。这个数字必须是**首轮通过率**，不是最终通过率。

| 统计口径 | 定义 |
|---|---|
| 首轮通过 | 第一次过 Gate 时全部判据通过 |
| 整改通过 | 首轮不通过，整改后通过 |
| **通过率** | 首轮通过次数 / 总 Gate 次数 |

### 冷鲜通项目实测

| Gate | 首轮结果 | 整改项 |
|---|---|---|
| Gate 0 | 有条件通过 | 范围冻结挪到 S1 |
| Gate 1 | 通过 | — |
| Gate 2 | **不通过**（真值 4/10） | 6 个缺陷，全部修复 |
| Gate 3 | 通过 | — |
| Gate 4 | 通过（含 1 项 E2E 挂起修复） | 无头 Chrome 挂起 |
| Gate 5 | 通过 | — |

**首轮通过率 4/6 = 67%**，低于 90% 目标。

**为什么如实报 67% 而不修饰**：这才是转型第一年的真实水平。把这个数字改成 100% 很容易（把 Gate 2 拆成两个 Gate 就变成 5/7=71%，或者干脆说"整改后通过就算通过"），但那样这个指标就失去了牵引作用。

**67% 说明什么**：Gate 表本身设得偏严（尤其 Gate 2 的真值 100% 要求），或者首个项目的 FDE 还不熟练。两者都是真话。第一年 67%，第二年目标 85%，第三年 90% —— 这个爬坡曲线才是可信的。

## 九、Gate 执行的三条纪律

### 纪律一：Gate 不通过不得进入下一阶段

没有"先往下做，后面补"。冷鲜通 Gate 2 卡了约 1.5 小时（真值从 4/10 到 10/10），这 1.5 小时是省下的——如果带病进 S3，6 个缺陷会在 S4 以 5 倍成本暴露。

### 纪律二：Gate 判定必须有证据附件

不能写"已检查通过"。每项判据后面要能指到具体文件/命令/截图/测试名。

### 纪律三：Gate 抽查机制

每 10 个项目随机抽 1 个做全流程复核。**抽查不是为了抓人，是为了发现"Gate 判定标准在实践中漂移了"。** 如果连续抽查都发现"该项其实没达到但放行了"，说明判据写得不够硬，要改 Gate 表而不是批评 FDE。
