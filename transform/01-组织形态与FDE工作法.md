# 01 组织形态与 FDE 工作法

> 58 人如何从「四支职能团队串行接力」变成「FDE + Agent 团队」。

---

## 一、从一个真实的一天说起

这是我在冷鲜通项目第 3 天（阶段 2，需求与规则引擎）的真实时间分配：

| 时段 | 在做什么 | 是不是"写代码" |
|---|---|---|
| 09:00–10:30 | 拆客户一句话需求，写「三能力簇」诊断，决定 6 项不做 | 否 |
| 10:30–12:00 | 和 Agent 一起把行业惯例形式化成 R01–R10 规则表 | 半 |
| 13:00–14:00 | 审 Agent 生成的规则代码，指出"R03 没绑作业阶段" | 是（审非写） |
| 14:00–15:30 | 建 12 个验证场景，为每个场景写"期望结论" | 否（定标准） |
| 15:30–17:00 | 跑真值校验，4/10，逐个查 | 半 |

**这一天里，我真正敲代码的时间约 1 小时（约占 12%）。** 剩下 88% 是：定义标准、拆判断、设期望、验结果。

这就是"人站两端"的字面意思。如果 FDE 的一天里写代码超过 50%，说明他退回到了"高级开发"角色，Agent 只是他的打字机——**这样的转型不会提升人均项目数**，因为瓶颈（人天）没变。

## 二、组织形态：从接力到网格

### 2.1 旧形态：四个职能串行接力

```
客户 ──→ 产品 ──→ Coding ──→ 质检 ──→ 项目管理 ──→ 交付
        (PRD)   (代码)    (测试报告)  (验收)
          ↓        ↓         ↓          ↓
       需求失真   重复造轮   测试被压缩  经验流失
       (返工22%)  (相似41%) (18缺陷/月) (流失18%)
```

**每一个箭头都是一次信息损失和一次排队等待。** 转型方案里列的五个痛点，全部落在这四个箭头上。

### 2.2 新形态：一个网格 = 1 FDE + Agent 团队 + 资产库

```
                    ┌──────────────────────────────────┐
                    │        FDE（1 人，不可替代）      │
                    │  ┌────────────┐  ┌────────────┐  │
   客户 ──────────→ │  │ 定义标准   │  │ 验收结果   │  │ ──────→ 交付
                    │  │ ·要什么    │  │ ·算不算合格│  │
                    │  │ ·不做什么  │  │ ·能否承诺  │  │
                    │  └─────┬──────┘  └─────▲──────┘  │
                    └────────┼───────────────┼─────────┘
                             │ 派活          │ 交证据
                    ┌────────▼───────────────┴─────────┐
                    │         Agent 团队（可复制）      │
                    │ 需求 Agent │ 设计 Agent │ 编码   │
                    │ 测试 Agent │ 文档 Agent │ 部署   │
                    └────────────────┬─────────────────┘
                                     │ 读写
                    ┌────────────────▼─────────────────┐
                    │   资产库（越用越厚，不因人而异）  │
                    │  代码库 │ Agent 库 │ SOP │ Gate  │
                    └──────────────────────────────────┘
```

**关键差别**：旧形态里，四个职能团队是**串联的瓶颈**；新形态里，Agent 是**并联的执行资源**，FDE 是唯一的串行点。

所以人均项目数的提升来自：**串行环节从 4 个降到 1 个**。不是"人变快了"，是"等待变少了"。

### 2.3 58 人怎么摆

| 角色 | 人数（M12 目标） | 来源 | 职责 |
|---|---|---|---|
| **FDE** | 12 | 原产品 4 + 原开发 5 + 原质检 2 + 原项管 1 | 定义标准 + 验收结果，一个 FDE 带 1–2 个项目 |
| **Agent 运营** | 4 | 原开发 3 + 原质检 1 | 维护 Agent 库、代码库、SOP、Gate；不直接交付项目 |
| **领域专家** | 6 | 原产品/行业老人 | 按需支撑 FDE，提供行业规则（如冷链定责惯例） |
| **平台/基础设施** | 4 | 原开发 | 统一 Token 网关、计量看板、凭据管理 |
| **交付保障** | 2 | 原项管 | 存量 23 个项目的维护协调 |
| **管理层** | 3 | 不变 | — |
| **其余（承接产能）** | 27 | 原各职能 | 随项目量增长自然消化，不裁员 |

**为什么 Agent 运营要 4 个人**：Agent 库如果没人维护，三个月就腐烂（模型升级后 prompt 失效、业务规则变了但 Agent 上下文没改）。这是转型最容易被忽略的隐性成本——**建库只是开始，运营才是长期投入**。

### 2.4 一个网格的边界

- **1 个 FDE 同时带 1–2 个项目**（M12）。再多就会退化成"项目协调员"，失去定义标准的时间。
- **网格之间共享资产库，不共享 FDE**。FDE 的上下文（客户、需求、判断）不可分割给两个人。
- **首个网格（冷鲜通）是标杆网格**，它的资产库是全公司的母版。

## 三、FDE 工作法

### 3.1 FDE 是什么，不是什么

| 是 | 不是 |
|---|---|
| 对客户承诺负责的人 | 项目经理（不管排期催进度） |
| 定义"什么算合格"的人 | 技术负责人（不选框架写核心代码） |
| 拆解判断、设定验证标准的人 | 产品经理（不只写 PRD） |
| 承担错误归责后果的人 | 代码审查员 |

一句话：**FDE 是"这个交付物能不能交出去"的唯一责任人。**

### 3.2 FDE 工时四分法（可考核）

这是把"人站两端"从口号变成可测量指标的方法：

| 类别 | 内容 | 目标占比 |
|---|---|---|
| **A 定义** | 需求深访、范围冻结、标准制定、规则形式化 | ≥25% |
| **B 验收** | 设验证场景、审 Agent 产出、找反面证据 | ≥25% |
| **C 编排** | 派活给 Agent、调 prompt、处理 Agent 失败重试 | ≤35% |
| **D 执行** | 亲自写代码/写文档 | ≤15% |

**红线**：`A + B ≥ 40%`。低于 40%，说明 FDE 掉进了 C 和 D，正在变成"AI 操作员"。

**冷鲜通项目实测**（按 10 周估算）：
- A 定义：约 35%（诊断、范围冻结、需求基线、规则形式化、真值设定）
- B 验收：约 30%（四层测试设计、缺陷排查、Gate 复核）
- C 编排：约 25%（派活、调 prompt、处理返工）
- D 执行：约 10%（少量核心算法亲自写）

**A+B = 65%，达标。** 这个数字本身是转型有效的证据——因为在传统模式下，A+B 通常不到 20%（大部分时间在 C 和 D）。

### 3.3 FDE 在每个阶段的具体动作

#### 阶段 1 诊断：只做三件事

1. **拆需求**：把客户一句话拆成能力簇，判断哪个是价值点、哪个是商品化能力
2. **定不做清单**：明确写出本期不做什么，并给理由（冷鲜通列了 6 项不做）
3. **算账**：传统模式 vs 新模式的人月对比，让客户知道 120 万花在哪

**这一步错了，后面全错。** 冷鲜通项目在这一步花了约 1.5 小时（占项目总时间 6%），但它决定了后面 9 周的方向。

#### 阶段 2 需求与规则：把行业经验变成可测试的规则

行业惯例在老师傅脑子里，FDE 的工作是把它**编号化**：

```
"看装车温度"           → R01 装车温度不合格
"看有没有私自开门"     → R03 途中开门超时
"看机组有没有停"       → R05 制冷机组非计划停机
"看数据全不全"         → R06 设备数据缺失
"看卸货拖了多久"       → R04 卸货超时
...
```

**编号化瞬间获得三个能力**：可测试（每条规则能单独造场景）、可解释（对客户说"按 R03 判的"）、可版本迭代（R03 加个条件不影响 R01）。

**FDE 在这一步最容易犯的错**：把规则写成代码。正确做法是写成**数据结构**（`{id, name, party, priority, test}` 的数组），引擎负责求值。这样业务方能参与维护，规则增删不改引擎。

#### 阶段 3 实现：审架构，不写业务代码

FDE 在这一步的产出是**边界决策**，不是代码：

- 技术栈选型（本项目选零依赖，理由是评委必须能一键跑起来）
- 模块边界（`rules.js` 和 `analyze.js` 必须分开，因为一个是事实层一个是判断层）
- 数据模型（温区存运单表不存货物字典，因为温区是交易约定不是货物属性）

**代码由 Agent 写，FDE 负责说"这个分法不对"。**

#### 阶段 4 测试：设期望，不写断言

FDE 在这一步的核心动作是**声明真值**：

```js
// FDE 写这个（在造数据时，不是看到结果后）
expect: { ruleId: 'R02', party: 'SHIP', note: '装车合格但出发后升温超 2℃/h' }
```

**断言由 Agent 写，期望由 FDE 定。** 这个分工不能反——如果让 Agent 同时定期望和写断言，它会（无意识地）让两者互相迁就，测试就变成了自证。

#### 阶段 5 部署与交付：对客户承诺

FDE 在交付时必须能回答三个问题：

1. **这套东西现在能干什么？**（演示三条角色路径）
2. **它不能干什么？**（7 条限制如实说，见 `docs/05` §5.2）
3. **出问题谁负责？**（FDE 本人）

**第三个问题是 FDE 存在的根本理由。** Agent 不会承担后果，所以必须有人。

## 四、FDE 认证（新人两周达 80% 产出的机制）

### 4.1 认证四关

| 关卡 | 内容 | 通过标准 |
|---|---|---|
| 一、读资产 | 读冷鲜通项目代码库 + 文档 + Gate 报告 | 能复述三个关键决策及其理由 |
| 二、跑复现 | 独立跑通 `verify-rules.js` + 全部测试 | 全绿，且能解释每条测试在防什么 |
| 三、做小项目 | 用同一套 SOP 交付一个内部小需求 | 通过 6 个 Gate，AI 覆盖率 ≥50% |
| 四、答辩 | 解释"为什么 R10 兜底而不是默认归承运方"这类问题 | 能说出取舍理由，不是背答案 |

### 4.2 为什么是两周

冷鲜通项目的完整资产（代码 3500 行 + 文档 2000 行 + Gate 报告）如果设计良好，读+跑+做小项目应该能在 10 个工作日内完成。

**如果两周做不到，说明资产化不够**——要么文档写成了流水账（读完不知道决策理由），要么代码没有可读性（注释缺失），要么 SOP 缺步骤（新人卡在某处无人可问）。

**所以 FDE 认证通过率是资产库质量的间接指标。** 这也是为什么 `metrics/05` 把"新人达标天数"列为核心指标。

### 4.3 认证不与薪酬挂钩（首年）

转型方案明确"不裁员、不降薪"。首年认证结果只用于：分配项目、内部标杆评选、培训资源倾斜。**不与薪酬挂钩，是为了降低抵触**——老员工的第一反应是"这是要淘汰我"，必须先消除这个恐惧，才谈得上配合。

第二年再考虑与晋升通道挂钩。

## 五、这一章要防的三个失败模式

| 失败模式 | 表现 | 本方案的防线 |
|---|---|---|
| **FDE 退化成 AI 操作员** | 工时四分法里 C+D >60% | A+B ≥40% 红线，按季度计量 |
| **组织形态改了但人心没改** | 认证通过率 <60%，老员工消极 | 首年不与薪酬挂钩；设内部标杆；不裁员承诺兑现 |
| **网格数量膨胀但资产库不厚** | 每个网格各建一套，重复造轮子 | Agent 运营 4 人专职维护共享库；不复用需书面说明理由 |
