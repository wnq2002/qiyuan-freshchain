# 02 Agent 库

> Agent 库是启元从 L1 到 L3 的核心资产。**没有 Agent 库，FDE 只是"用 AI 的人"；有了 Agent 库，组织才具备不因人而异的交付能力。**

---

## 一、Agent 与 Prompt 的区别

这是建库第一天必须讲清楚的事，否则库里会塞满一堆复制粘贴的 prompt。

| | Prompt | Agent |
|---|---|---|
| 形态 | 一段话，用完就走 | 有名字、有职责、有输入输出契约、有验收标准 |
| 复用 | 每次重新写 | 调用即用，参数化 |
| 维护 | 无 | 有版本、有 owner、有回归用例 |
| 失败处理 | 靠人重试 | 有明确失败模式与降级路径 |
| 归属 | 个人 | 组织 |

**判断标准**：如果一段 prompt 只被用过一次，它是 prompt；如果同类任务要反复做，它就该被建成 Agent。

## 二、六个 Agent（冷鲜通项目实证）

以下六个 Agent 全部在冷鲜通项目中实际使用过，不是规划。

### A1 · 需求拆解 Agent

| 项 | 内容 |
|---|---|
| **职责** | 把客户的一句话需求拆成能力簇，输出"价值点判断 + 不做清单" |
| **输入** | 客户原话、行业背景、预算工期 |
| **输出** | 能力簇表（表面诉求/真实问题/行业现状/难度）、不做清单及理由 |
| **上下文** | 行业痛点清单、竞品能力边界、历史项目的范围失控案例 |
| **验收** | 每个"不做"项必须给出理由；价值点判断必须回答"为什么客户愿意为这个付钱" |
| **失败模式** | 拆得太多（什么都做）→ 强制输出不超过 3 个 P0 能力 |
| **冷鲜通实证** | 把一句话拆成 C1 监控 / C2 定责 / C3 问询，判定 C2 是价值点，列 6 项不做 |

**这个 Agent 最容易被低估。** 它的产出是 `docs/01`，看起来只是"写了个文档"，但后续 9 周的方向全部由它锁定。**FDE 在这一步的审阅时间应该是所有环节里最长的。**

### A2 · 规则形式化 Agent

| 项 | 内容 |
|---|---|
| **职责** | 把行业经验/客户口语规则转成带编号、可测试的规则数据结构 |
| **输入** | 领域专家访谈纪要、行业规范、客户实操习惯 |
| **输出** | 规则表：`{id, name, party, priority, why, test(ctx)}` |
| **上下文** | 责任主体字典、优先级设计原则、规则必须绑定作业阶段 |
| **验收** | 每条规则：能单独造场景、有明确责任主体、有业务含义说明、优先级唯一 |
| **失败模式** | 规则之间互相重叠（两条规则同时命中）→ 强制走优先级短路求值 |
| **冷鲜通实证** | R01–R10，含一次重大返工：R03 最初没绑作业阶段，把"卸货开门"判成"途中私自开门" |

**踩坑已转为 Agent 上下文**：

```
【强制约束】任何涉及"作业行为"的规则，必须限定时间域：
  · 装车阶段：depart_loaded 之前
  · 运输阶段：depart 之后、arrive 之前
  · 卸货阶段：arrive 之后
理由：同一个物理动作在不同阶段责任归属相反。冷鲜通 R03 曾因此判反责任方。
```

### A3 · 场景与真值 Agent

| 项 | 内容 |
|---|---|
| **职责** | 为每条规则造 1 个"必然命中"的验证场景，并声明期望结论 |
| **输入** | 规则表、物理模型参数 |
| **输出** | 场景数组：`{no, sim参数, events, expect: {ruleId, party, note}}` |
| **上下文** | 物理模型（制冷周期/开门升温/停机趋近/货物带热衰减）、"期望必须在造数据时写" |
| **验收** | 每条规则至少 1 个场景；场景数据物理上自洽；期望写在造数据时而非看到结果后 |
| **失败模式** | 场景造得"刚好卡线"（数据刚好越过阈值）→ 强制留 20% 余量 |
| **冷鲜通实证** | 12 个场景（10 已交付 + 2 在途），首轮真值校验 4/10 |

**这个 Agent 的价值在于"互不知情"**：它写期望值，另一条路径的引擎做判定，两边不通信。这样校验才有意义。

**踩坑已转为 Agent 上下文**：

```
【强制约束】造场景数据时，先确认喂给模拟器的参数完整。
冷鲜通事故：verify-rules.js 漏传 cargoHeat 参数，导致 003 场景一直判 R08。
排查时误以为是规则链问题，写了 8 个调试脚本才定位。
→ 造数据的代码和被测代码一样需要被怀疑。
```

### A4 · 领域引擎 Agent

| 项 | 内容 |
|---|---|
| **职责** | 实现判定引擎：上下文化、超温识别、空洞检测、规则短路求值 |
| **输入** | 规则表、数据模型、物理约束 |
| **输出** | `analyze.js` + `rules.js` + `rule-utils.js` |
| **上下文** | 纯函数要求（无 Date.now/无 random）、模块边界（事实层 vs 判断层）、确定性 |
| **验收** | 同输入两次调用结果 `deepEqual`；无循环依赖；规则增删不改引擎 |
| **失败模式** | 把 `Math.random()` 或 `Date.now()` 混进判定 → 单测"判定确定性"拦截 |
| **冷鲜通实证** | 288 行 analyze + 333 行 rules + 47 行 utils，单测 20 项全过 |

**踩坑已转为 Agent 上下文**：

```
【强制约束】规则分不开两件事时，先怀疑领域模型，不要调阈值。
冷鲜通事故：R02（预冷不足/货物带热）与 R07（制冷不足）在旧模型下数据形态相同，
调阈值只能左右搬分界线，按下一头翘另一头。
解法：模拟器引入 cargoHeat 指数衰减热源，两类物理过程天然可分。
→ 规则分不开 = 模型没建对。
```

### A5 · 验证 Agent

| 项 | 内容 |
|---|---|
| **职责** | 写四层测试：单元/集成/端到端/性能，且必须能证明"用真实浏览器渲染" |
| **输入** | 实现代码、接口契约、业务路径 |
| **输出** | 测试套件 + 验证报告（含缺陷复盘） |
| **上下文** | "测接口不等于测用户能不能用"、黑名单脱敏断言、无头浏览器挂起陷阱 |
| **验收** | 不只测 200；E2E 必须 dump 真实 DOM；脱敏用字符串黑名单；缺陷如实记录 |
| **失败模式** | 只断言状态码 → 强制每层至少一个"业务语义断言" |
| **冷鲜通实证** | 44 项测试（21 单测 + 17 集成 + 6 E2E），3 秒跑完 |

**踩坑已转为 Agent 上下文**：

```
【强制约束】无头 Chrome --dump-dom 不能用 execFileSync。
症状：Chrome 打印完 DOM 后进程不退出（headless 下驻留），execFileSync 永久挂起。
解法：spawn + 轮询检测 </html> + 出现即 kill + 20 秒硬超时兜底。
```

### A6 · 交付文档 Agent

| 项 | 内容 |
|---|---|
| **职责** | 写运行说明、验证报告、边界声明；保证"换个人能复现" |
| **输入** | 代码、测试结果、Gate 报告、缺陷记录 |
| **输出** | `docs/04` 设计说明、`docs/05` 验证报告、`docs/06` 交付说明 |
| **上下文** | 只写跑过的、不能证明的必须列、命令必须可复制 |
| **验收** | 每条结论有证据；"不能证明"部分不得为空；复现命令实际跑过 |
| **失败模式** | 写成"功能正常/性能良好"式空话 → 强制每个论断后跟具体数字或文件路径 |
| **冷鲜通实证** | 5 份文档，`docs/05` 含 9 条缺陷复盘 + 7 条边界声明 |

## 三、Agent 上下文规范（写 Agent 的模板）

每个 Agent 必须有六段，缺一段就是 prompt 不是 Agent：

```markdown
## 角色
一句话说清它是什么（不是"你是一个资深专家"这类废话）

## 职责边界
· 做什么（3–5 条）
· 明确不做什么（防止越界，至少 2 条）

## 输入契约
字段名、类型、必填与否、示例

## 输出契约
结构、必含字段、格式约束

## 强制约束
【强制】xxx —— 每条约束后面必须跟"为什么"，且理由必须来自真实踩坑

## 验收标准
可机器判定或可人工快速核对的条目
```

**"强制约束"是最有价值的一段。** 它积累的是**组织踩过的坑**，不是通用最佳实践。通用最佳实践模型本来就知道，写进去没价值；冷鲜通 R03 判反责任方这种事，只有踩过才知道。

**所以 Agent 库的价值随时间增长，而不是随时间衰减。** 这也是为什么必须有专职 Agent 运营。

## 四、Agent 库的维护机制

### 4.1 版本与 owner

| 字段 | 规则 |
|---|---|
| 版本 | 语义化（v1.2.3）。改约束=minor，改契约=major，改措辞=patch |
| owner | 必须有唯一负责人（Agent 运营团队成员） |
| 回归用例 | 每个 Agent 至少 1 个"输入→期望输出"用例，改完跑一遍 |
| 变更记录 | 每次改动的理由（尤其"为什么加这条约束"） |

### 4.2 三个月腐烂检查（强制）

每季度对每个 Agent 做三件事：

1. **重跑回归用例** —— 模型升级后输出可能漂移
2. **检查约束是否过时** —— 业务规则变了，旧约束可能变成错误引导
3. **统计调用次数** —— 连续一个季度零调用的 Agent，归档或删除

**为什么必须强制**：Agent 库最大的风险不是建不起来，是建起来后腐烂而没人发现。腐烂的 Agent 比没有 Agent 更危险——它会让新人以为"这事有标准做法"，然后照着过时的标准做。

### 4.3 谁可以改 Agent

| 角色 | 权限 |
|---|---|
| Agent 运营 | 可改任何 Agent（含契约） |
| FDE | 可提修改建议，可加"强制约束"（需 owner 复核） |
| 其他人 | 只读 |

**FDE 有"加约束"的权限但没有"改契约"的权限**，这是刻意的：约束是踩坑经验的沉淀（FDE 最清楚新坑），契约是接口稳定性（不能随便动，否则所有调用方都要改）。

## 五、Agent 库与代码库的关系

两者不是一回事，容易混：

| | 代码库 | Agent 库 |
|---|---|---|
| 存什么 | 可复用的**代码资产**（登录、权限、报表、规则引擎模式） | 可复用的**执行能力**（怎么把需求拆开、怎么造验证场景） |
| 谁用 | 开发者（含 Agent） | Agent（由 FDE 驱动） |
| 复用方式 | import / 复制模块 | 调用（派活） |
| 沉淀什么 | 技术方案 | 判断方法与踩坑经验 |

**代码库回答"用什么写"，Agent 库回答"怎么想"。** 转型方案要求两库都是"默认知识资产"，缺一个都不成立——只有代码库，Agent 每次都要重新摸索判断方法；只有 Agent 库，Agent 每次都要重写登录模块。

## 六、冷鲜通项目的 Agent 库实际产出

| 资产 | 位置 | 可复用范围 |
|---|---|---|
| 需求拆解方法（三能力簇 + 不做清单） | `docs/01` | 所有定制项目阶段 1 |
| 规则形式化模板（数据结构 + 优先级短路） | `docs/03` + `src/domain/rules.js` | 所有"专家经验→可测试规则"类项目 |
| 真值校验方法（场景声明期望 + 引擎独立判定） | `tests` + `scripts/verify-rules.js` | 所有判定类系统 |
| 四层测试框架（含无头浏览器坑） | `tests/*.test.js` | 所有 Web 交付项目 |
| 零依赖技术栈方案 | `src/` | 所有需要"客户能一键跑"的交付 |
| Gate 表 | `gates/` + `transform/gates/` | 所有项目 |

**这六项中，第 3 项（真值校验）是本次交付最有复用价值的方法论。** 它解决了一个普遍问题：怎么验证"判断类系统"的正确性。这个问题的解法在行业内并不常见，大多数团队只会测"接口通不通"。
