# 启元软件 · 冷鲜通冷链监控与责任判定系统

> 启元软件（Qiyuan Software）首个 AI Native 场景网格交付物
> FDE：总经理兼任 ｜ 客户：冷鲜通冷链 ｜ 周期：10 周 ｜ 预算：120 万

## 这是什么

一套给冷链 3PL 用的**在途温控监控 + 责任判定 + 客户问询**系统。

客户原话只有一句：

> "给我做一个能实时看住冷链、出了事能说清是谁的责任、客户问起来能马上回答的系统。"

本系统的核心不是温度看板，而是**把冷链纠纷里靠吵架解决的责任认定，变成可编号、可测试、可解释的规则判定**。

## 三个能力

| 能力 | 一句话 | 入口 |
|---|---|---|
| C1 实时监控 | 在途运单温度曲线与超温告警 | `/` 质控看板 |
| C2 责任判定 | 每票异常输出责任主体 + 规则编号 + 证据链 + 置信度 | `/waybill/:no` 运单详情 |
| C3 客户问询 | 按运单号查询，与内部看板同源同值的对外结论 | `/track` 客户问询 |

## 快速开始

零依赖，只需 Node.js ≥ 22（内置 `node:sqlite`）：

```bash
node scripts/seed.js      # 初始化数据库与虚构数据
node src/server.js        # 启动，默认 http://localhost:8787
```

浏览器打开 `http://localhost:8787`。不需要 `npm install`，不需要数据库服务，不需要联网。

## 验证（三条命令）

```bash
node scripts/verify-rules.js       # 规则真值校验：10 个场景，引擎独立判定 vs 预置期望
node --test "tests/*.test.js"      # 43 项自动化测试（单元 20 + 集成 17 + E2E 6），约 2.7 秒
```

期望输出：`全部命中真值 ✔` / `pass 43 / fail 0`。

端到端测试用**无头 Chrome 渲染真实 DOM** 后断言（不只是测接口）。环境无 Chrome 时自动跳过并标记，不伪装通过。

## 十条判定规则

| 编号 | 规则 | 责任主体 | 优先级 |
|---|---|---|---|
| R01 | 装车温度不合格 | 发货方 | 10 |
| R06 | 设备数据缺失 | 设备方 | 20 |
| R05 | 制冷机组非计划停机 | 设备方 | 30 |
| R03 | 途中开门超时 | 承运方 | 40 |
| R04 | 卸货超时 | 收货方 | 50 |
| R02 | 预冷不足 | 发货方 | 60 |
| R07 | 多次小幅超温累积 | 承运方 | 70 |
| R09 | 温控合格但到货拒收 | 收货方 | 80 |
| R08 | 温区内正常 | 无责任方 | 90 |
| R10 | 证据不足 | 无法判定 | 999 |

短路求值，首个命中即返回。详见 `docs/03-需求基线MoSCoW.md`。

**几个刻意的设计选择**：

- **R01 排第一**：装车就超标的，途中一切温升都是果不是因，先判因果链上游。
- **R10 兜底而非默认归承运方**：默认归责是最常见的产品设计错误——它让系统在证据不足时假装有结论，代价由一方承担。
- **在途运单不判责**：输出 `PENDING / 在途未定责`、`confidence: null`。货还在路上就出结论等于提前定罪。

## 边界（务必先读）

- 全部数据**教学虚构**，不含任何真实客户信息、真实账号、真实凭据。
- 温度数据由物理模型生成，**未接真实记录仪**；接入契约见 `docs/04-系统设计.md` §5.4。
- 责任判定规则按行业通行惯例形式化，**未与冷鲜通真实业务校准**，**不构成法律意见**。
- 当前**无鉴权**，任何人拿到 URL 都能访问内部视图。生产环境必须加登录与角色隔离。
- 单探头假设，多探头冲突裁决未实现。

详见 `docs/05-验证报告.md` §5.2（7 条不能证明的事）与 `docs/06-交付说明.md` §5（5 项技术限制）。
